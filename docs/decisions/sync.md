# Sync

<!-- Part of docs/DECISIONS.md, the index of decisions (851-2791). -->

- **Local-first:** apps keep a local SQLite copy of the user's data and query only that. Derived values (e.g. daily totals) are computed locally.
- **Change log:** every write to a user's data appends to their change log, with a sequence number that increases per user and has no gaps. Clients pull changes after their cursor, bootstrap new devices from snapshots, and get live notices over a WebSocket.
- **Generic:** the protocol isn't specific to health, so lil mail and lil calendar can reuse it. It's specified in `docs/SYNC.md`.
- **Loading snapshots** (851-2859): records go to a staging table without indexes, then into their table in one transaction, in primary key order, with the table's other indexes dropped and built again in that transaction. Upserting them in the server's order put random HealthKit IDs all over the primary key's index, and inserts slowed down as the database grew (36 µs a record at 200,000, 64 µs at 1,000,000). The cost: the Mac shows the new data all at once, at the end, rather than as it loads, and the last transaction holds the database's writer for a few seconds per million records (other writes wait for a bootstrap anyway).
- **Showing a bootstrap's progress** (851-2946): the Mac's sync footer counts items left, in the iPhone's words ("1,234,567 items left", `ItemsCopy`), not snapshot parts. Each stage counts its own records: downloading (from the manifest's per-part `records`, so the server needed no new field), then saving to the Mac (records staged or loaded, after each batch), then "Finishing up…" over a moving bar for the final transaction, which can't report progress. A catch-up of more than a page counts the changes left (`head - cursor`, "487,650 changes left"), not items, since a record can change more than once; an everyday sync is one page and goes straight to up to date.
- **When the Mac shows the sync footer** (851-2991): only while sync has something to say. Up to date, the sidebar has no footer, and its list runs to the bottom. A first sync, being offline and a failed pull (backing off) show it at once: the first takes minutes, and the others need the person's attention. A pull that isn't done (the first after launch, or a catch-up of several pages) shows it once it has run for 2 seconds, counted from its first status rather than from each page, so everyday syncs never flash it: they're one page, done in well under a second, and once up to date don't change the status at all. Not animated. "Updated X ago" is gone rather than moved: with live notices, up to date means now, so it read "Updated now" nearly always. How fresh the data is depends on the iPhone's last upload, which `lil-health status` (`sync_status`) reports, and the Sync action answers with the time it synced.
