# Sync

<!-- Part of docs/DECISIONS.md, the index of decisions (851-2791). -->

**The protocol is specified in [`docs/sync/protocol.md`](../sync/protocol.md).** This file records the decisions behind it.

- **Local-first:** apps keep a local SQLite copy of the user's data and query only that. Derived values (e.g. daily totals) are computed locally.
- **Change log:** every write to a user's data appends to their change log, with a sequence number that increases per user and has no gaps. Clients pull changes after their cursor, bootstrap new devices from snapshots, and get live notices over a WebSocket.
- **Generic:** the protocol isn't specific to health, so lil mail and lil calendar can reuse it.
- **Loading snapshots** (851-2859): records go to a staging table without indexes, then into their table in one transaction, in primary key order, with the table's other indexes dropped and built again in that transaction. Upserting them in the server's order put random HealthKit IDs all over the primary key's index, and inserts slowed down as the database grew (36 µs a record at 200,000, 64 µs at 1,000,000). The cost: the Mac shows the new data all at once, at the end, rather than as it loads, and the last transaction holds the database's writer for a few seconds per million records (other writes wait for a bootstrap anyway).
- **A new entity is caught up alone** (851-3222): a release that starts storing an entity loads only its parts of the latest snapshot, then pulls the changes from the snapshot to its cursor for it, instead of bootstrapping everything again (`docs/sync/protocol.md` › Schema changes). Bootstrapping again downloaded and reloaded a Mac's whole Health copy, millions of records, for a handful of cards (851-3192). Chosen over a cursor per entity, which would make every pull and the live notices track several positions: the catch-up runs once, before the next pull, and leaves one cursor. It needs nothing new from the server (the change feed's `limit` keeps it from passing the cursor), and the change feed's `entities` filter (851-3221) only makes it smaller: the catch-up asks for only the new entity's changes. A new field of an entity already held still bootstraps (a `syncSchema` bump), since every record of it needs the field, which only a snapshot carries for records that didn't change.
- **Showing a bootstrap's progress** (851-2946): the Mac's sync footer counts items left, in the iPhone's words ("1,234,567 items left", `ItemsCopy`), not snapshot parts. Each stage counts its own records: downloading (from the manifest's per-part `records`, so the server needed no new field), then saving to the Mac (records staged or loaded, after each batch), then "Finishing up…" over a moving bar for the final transaction, which can't report progress. A catch-up of more than a page counts the changes left (`head - cursor`, "487,650 changes left"), not items, since a record can change more than once; an everyday sync is one page and goes straight to up to date.
- **When the Mac shows the sync footer** (851-2991): only while sync has something to say. Up to date, the sidebar has no footer, and its list runs to the bottom. Anything else (the pull at launch, a catch-up of several pages, a first sync, being offline, a failed pull backing off) shows it once sync has gone 2 seconds without being up to date, counted from the first such status rather than from each page or retry, and until it's up to date again. Everyday syncs never flash it: they're one page, done in well under a second, and go from up to date straight to up to date again (`.syncing` only follows a page with more after it). Nor does a failure the first retry fixes, about a second later, such as being offline for a moment after waking. Not animated: it would slide every row with the list's inset. "Updated X ago" is gone rather than moved: with live notices, up to date means now, so it read "Updated now" nearly always. How fresh the data is depends on the iPhone's last upload, which `lil-health status` (`sync_status`) reports, and the Sync action answers with the time it synced.
