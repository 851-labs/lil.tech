# Distribution and CI

<!-- Part of docs/DECISIONS.md, the index of decisions (851-2791). -->

- **Team:** every app is signed by team `WH4QW9ND3J`. Debug builds are signed with Apple Development, so macOS keeps privacy permissions across rebuilds.
- **Versioning:** each app has its own version, shared across its platforms and tagged like `messages/v0.1.0` or `health/v0.1.0`.

## Mac apps

- **Direct download only**, never the Mac App Store. Not sandboxed.
- **Signing:** Release builds are signed with Developer ID, with the hardened runtime and a secure timestamp.
- **Notarization:** `notarytool` with an App Store Connect API key, saved in the keychain profile `lil-notary`.
- **Packaging:** a signed, notarized DMG, used both for first downloads and as the Sparkle update.
- **Updates:** Sparkle, with EdDSA-signed updates. Each app has its own key, in Alexandru's login keychain (account `lil-<app>`) and backed up in 1Password. The public key is in the app's Info.plist (for lil health, the Mac target's `LilHealth-Info.plist`). lil messages' first key was lost without a backup and replaced in October 2026 (851-2685). Installed copies still update, through Sparkle's key rotation for Developer ID-signed apps, as long as the Developer ID certificate doesn't change in the same release.
- **Releases:** GitHub Releases host the DMGs. Each app's appcast is committed to the repo (`appcasts/<app>.xml`) and served from `raw.githubusercontent.com`, because GitHub's "latest release" URL is repo-wide.
- **lil health for Mac** (851-2632) ships the same way as lil messages: `scripts/release health <version>`, tags `health/v<version>`, and `appcasts/health.xml`, which starts with no releases. Its icon is the iPhone's artwork shaped for macOS: Apple's 824-point body on a 1,024 canvas, with continuous corners and a soft shadow. Its session lives in the data protection Keychain, which needs the app's keychain access group, so the Mac app claims it (`LilHealth.entitlements`) and its releases carry a Developer ID provisioning profile, which Xcode makes and renews (`-allowProvisioningUpdates`). Without it, a Developer ID build couldn't keep its session (`errSecMissingEntitlement`), while Debug builds, with their development profile, could.
- **The `lil` command** (851-2842): each app's command line tool is `lil-<app>`, and `lil <app> …` runs it, as git runs `git-<command>`, so apps never install commands that collide. `lil` (`LilCLI`, a small Swift executable) looks inside the installed app first (Launch Services' app for `tech.lil.<app>`, then `Contents/MacOS/lil-<app>`), which survives the app moving and Sparkle updating it, then on `PATH` (dev builds, a future Homebrew install), and `exec`s it, so input and output (an MCP server's protocol), signals and exit status are the tool's. `lil` and `lil help` list the apps with a tool (`lil-<app> --describe`), and `lil help <app>` runs `lil-<app> --help`.
  - **`lil mcp`** (851-2897): one local MCP server on standard input and output with every installed app's tools, so an agent adds `lil mcp` once rather than a server per app. It's `lil`'s own (`LilCLI`, on the same pinned swift-sdk as the apps' servers), so `mcp`, like `help`, is a reserved word: no app may be called either, and `lil mcp` never runs a `lil-mcp`.
    - **Finding servers:** the known apps (`Dispatcher.apps`, the list `lil help` uses) whose tool `locate(app:)` finds, inside the installed app first and then on `PATH`. Not any `lil-<something>` on `PATH`: as with `--describe`, a tool `lil` doesn't know could do anything with an argument it doesn't expect. A new app only adds its name to `Dispatcher.apps`, and each app's `lil` is the newest installed (851-2858), so it knows every app.
    - **Children:** `lil mcp` runs each app's `lil-<app> mcp` as a child process over pipes and talks to it as an MCP client (the SDK's `Client`), all at once, each given 10 seconds to initialize and list its tools. A tool without `mcp`, or one that fails to start, is skipped, with a line on standard error. They start when `lil mcp` does, before it answers `initialize`, since its instructions include theirs and the SDK's server fixes its instructions when it's made. They end with it. A child that exits is started again at the next request to it, once. If that fails, its tools answer with `isError` ("lil health's server stopped.") from then on.
    - **The combined server** is named "lil", with `lil --version` as its version. Its instructions say tools are named `<app>.<tool>`, then give each app's own instructions under its name. It lists each child's tools as `<app>.<name>` (`health.summary`), with their titles, descriptions, schemas and annotations unchanged, and their resources with their URIs unchanged, since each app has its own scheme (`health://catalog`). `listChanged` is false: the servers are found once.
    - **Requests:** a call splits its name at the first dot (app names have none) and goes to that app's server under the tool's own name. The result comes back as it is (`structuredContent`, `isError`), and a protocol error stays a protocol error. An unknown app or tool is invalid params (`-32602`), as an unknown tool is for an app's own server. A resource read goes to the server that listed its URI. Cancellation and progress aren't forwarded, since every tool is read-only and quick.
    - **Access stays per app:** each child checks and logs its own app's switch, so `lil mcp` adds no check of its own. It passes its own parent's name to the children in `LIL_CALLING_PROCESS` (`claude (via lil mcp)`), since their parent is `lil`.
    - **Dots in tool names** were checked with real clients first (2026-10-21), because the remote combined server (851-2900) follows the result. The MCP spec allows `A–Z a–z 0–9 _ - .` and gives `admin.tools.list` as an example. MCP Inspector and Codevisor list and call `health.summary` unchanged. Claude Code shows the model `mcp__<server>__health_summary`: it maps every character the Anthropic API doesn't allow in tool names to `_`. The call still reaches the server as `health.summary`. The separator is one constant (`LilMCPServer.separator`).
    - **Tests** use `lil-example`, a test-only executable that serves one tool and one resource, next to the built `lil-health` on a synthetic database in a temporary home. Only possible once a second real app exists: checking `lil mcp` against two real apps' servers.
  - Every Mac app bundles `lil` in `Contents/MacOS` (lil health first). An app target can't embed a package's executable, so the app's project has a thin `lil` tool target that builds the package's `Sources/lil/main.swift`, and the app copies it in with Code Sign On Copy, so it's signed (hardened runtime) before the app is sealed. The Developer ID export re-signs both, the DMG's notarization covers it, and `scripts/release` checks its signature first.
  - lil health bundles `lil-health` (851-2843) the same way: a thin `lil-health` tool target in `LilHealth.xcodeproj` builds `LilPackage/Sources/lil-health/main.swift` (the package's `lil-health-dev`) against `HealthCLI`, the app copies it into `Contents/MacOS` with Code Sign On Copy, and `scripts/release` checks its signature too. Bundle ID `tech.lil.health.cli`.
  - **Install Command Line Tool…** in the app menu copies it into `/usr/local/bin` (asking for an administrator's password if needed) or `~/.local/bin`. A copy, not a link into the app, which would break when the app moves; `lil` finds the apps itself. It replaces a `lil` already there only if that one is older, and leaves another command named `lil` alone. `lil --version` is the build number of the app it shipped in, the commit count, so copies from different apps compare.
  - **Keeping it current** (851-2858): when the app opens, it replaces an installed `lil` older than the one it bundles, so a Sparkle update (which relaunches the app) reaches `lil` too. Silently where this account can write the folder (`~/.local/bin`, or a `/usr/local/bin` it owns, as Homebrew's is on Intel Macs). Where only an administrator can, it offers to with an alert on the main window, once per bundled version, rather than asking for a password nobody expected; Install Command Line Tool… does the same later. It never installs a `lil` where there was none, and leaves links alone (Homebrew's, or the user's). It runs nothing either: it reads both versions from the info section the `lil` target embeds (`tech.lil.cli`, `CFBundleVersion`), so another command named `lil` isn't run at every launch. Not the other option, an installed `lil` that `exec`s a newer one inside an app: the file on disk would stay old, and `lil --version` would no longer say what's installed.

## iOS apps

- **TestFlight and the App Store**, which HealthKit requires. Release builds are signed with Apple Distribution and uploaded to App Store Connect.
- **Uploads:** `scripts/release health-ios <version>` archives with the version, shared with the Mac app, and the commit count as the build number, then uploads with the Apple account signed in to Xcode (cloud signing), not an API key. Cloud signing needs an Admin key: an App Manager key's export fails on cloud signing permissions. The Admin team key "lil.tech CI" replaced the App Manager one in October 2026 (851-2827). Releases always set the version on the command line; the projects' `MARKETING_VERSION` is a placeholder for local builds (851-2817).
- **Export compliance:** `ITSAppUsesNonExemptEncryption` is `NO` in the iOS app's Info.plist, so builds don't wait for the question in App Store Connect. The app only uses exempt encryption: HTTPS, the Keychain, and SHA-256 hashing.

## Everywhere

- **CI:** the TypeScript and Pixelbook checks run locally, before every commit, in a lefthook pre-commit hook (`lefthook.yml`, `scripts/check`), only for the parts a commit touches. The Swift checks run on GitHub, on our own Mac minis (851-2787). GitHub also deploys: PR previews, then staging and prod on merge to `main`.
  - Why local at first: GitHub's Swift workflow took 6–11 minutes, mostly a cold runner restoring caches, while the same checks take about 70 seconds on a warm Mac. But the Swift checks took 2–10 minutes per commit in the hook as the package grew, longer with two worktrees checking at once.
  - **Two workflows** (851-2826): `pr.yml` runs everything for a pull request, and `main.yml` everything after a merge, so "what runs on my PR" is one file. Before, `services.yml`, `swift.yml` and `pixelbook.yml` each mixed PR and `main` jobs, with their own triggers, concurrency and path filters. Each starts with one `changes` job (the composite action `.github/actions/changes`, which holds both path lists) that decides which parts are affected; the other jobs skip what isn't. Shared steps are a reusable workflow (`swift-check.yml`, the Swift check both call) and composite actions (`setup-services`, `changes`, and `comment`, which posts or updates a PR comment by its marker).
  - **`pr-ok`** ends `pr.yml`: it needs every other job, runs even when one failed or the run was cancelled (`if: always()`), and passes only when each passed or was skipped. Branch protection needs only that one check, rather than job names that path filters sometimes skip (a skipped required check counts as passed, and one that never reports blocks the merge). A failed preview deploy fails it too, so rerun a flaky one. It's required by the "Protect main" ruleset (a GitHub setting, not in the repo), which doesn't require branches to be up to date with `main`.
  - **Concurrency is per job,** since cancelling a whole run would stop a deploy halfway. A PR's new push cancels its previous Swift check, while its preview deploy and teardown share a group that never cancels, so a teardown waits for a running deploy. Since a push's preview joins that group only after its `changes` job, the preview checks the PR is still open before deploying, so a PR closed right after a push isn't redeployed after its teardown. In `main.yml` nothing is cancelled: the deploy (and Pixelbook's pointer) queue in the order of the merges (`queue: max`; the default keeps only one waiting and cancels the others), and each merge's Swift check runs on its own. Running `main.yml` by hand re-checks main's Swift and never deploys.
  - **Pixelbook's jobs** (paused, 851-2816) sit in `pr.yml` and `main.yml` behind `if: false && …`, rather than in a by-hand `pixelbook.yml`: run by hand, that workflow's jobs never matched its event anyway, and keeping them with the rest means turning them back on is deleting `false &&`.
  - **The Swift check** (`swift-check.yml`, called by `pr.yml` and `main.yml`) runs `scripts/check --swift` for pull requests and merges to `main` that touch Swift, on the self-hosted Mac minis Codevisor builds on (label `codevisor-macos-arm64`, in the "Mac minis" runner group). The group allows only codevisor and lil.tech, but any of their workflows on any ref: GitHub only lets a group allow a workflow at refs that exist, so it can't allow pull requests' (`refs/pull/<n>/merge`). Main's builds are kept apart from pull requests', and both start over past 40 GB, since the disks are Codevisor's too. They keep their builds between runs, outside the checkout (`LIL_CHECK_SCRATCH`), so a run takes minutes. It picks an Xcode with Swift 6.4 through `DEVELOPER_DIR`, never `xcode-select`, which would change the machine for Codevisor's jobs too.
  - **The repo is public:** a fork's pull request runs no workflow until a maintainer approves it (the repo's policy covers every outside contributor, not just first-timers). That approval is the barrier: a fork's PR runs its own copy of the workflows, so it could drop the job's check of the head repository, or add a workflow for the minis' label. Never approve a fork's run that changes `.github/`.
  - Fork PRs get a skipped Swift check and no preview, so their `pr-ok` passes without them, as `check` did before. The approval above is what stands in for those checks.
  - The trade-off: nothing re-checks the TypeScript of a commit made with the hook skipped, or merges that combine changes. Keep commits passing, and merge only branches that are up to date with `main`, which the ruleset leaves to us.
- **No analytics or crash reporting** in the apps. The server uses Cloudflare's Workers Logs and Effect tracing, with no third-party observability.
