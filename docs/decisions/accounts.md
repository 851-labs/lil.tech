# Accounts

<!-- Part of docs/DECISIONS.md, the index of decisions (851-2791). -->

- **Auth:** our own, written in Effect. Sign in with Apple and Sign in with Google.
  - The apps sign in natively. The server verifies the provider's ID token and issues its own session: short-lived access tokens and rotating refresh tokens.
  - **Sign in with Apple:** the app sends Apple the SHA-256 (hex) of a random nonce and sends us the nonce with Apple's identity token. The server checks Apple's signature (keys fetched through Cloudflare's cache), the issuer, the audience (`tech.lil.health` for the iPhone's native sheet, or the Mac's Services ID `tech.lil.health.web`, below), expiry, a 10-minute maximum age and the nonce. Apple only gives the name on the first sign-in, so the app sends it then.
    - **On the Mac, through Apple's web page** (851-2678): a Developer ID–distributed Mac app can't use the native sheet (Developer ID profiles can't carry the Sign in with Apple capability, 851-2538). The Mac opens `appleid.apple.com/auth/authorize` with the Services ID `tech.lil.health.web` (grouped under `tech.lil.health`, so the Apple user ID is the same) in a web authentication session. Apple posts the result to `POST /v1/auth/apple/web` (registered for `api.lil.tech` and `api.staging.lil.tech`), which redirects to `tech.lil.health://apple-signin` with the identity token, Apple's authorization code (for revoking, below), `state` and the first sign-in's name. It refuses posts from another web origin or over 16 KB with an `error` in the same redirect, and isn't rate limited (the sign-in that follows is). The app signs in through `POST /v1/auth/apple`, which accepts either audience. The iPhone keeps the native sheet. Previews can't be registered with Apple and keep the test-account sign-in.
  - **Sign in with Google:** the apps use Google's native sign-in with a nonce, like Apple (Google gets its SHA-256, we get the nonce), and send us the ID token. The server checks Google's signature, the issuer, the audience and authorized party (our OAuth client IDs, listed in `src/auth/Google.ts`), expiry, a 10-minute maximum age, the nonce and a verified email. Without client IDs listed, the endpoint answers 503.
    - **Google Cloud** (851-2538): the project "lil tech" (`lil-tech-851`, in the 851.sh organization, owned by alexandru@851.sh). Its consent screen is "lil health", external and in production, with only `openid`, `email` and `profile`, so it needs no Google review. Its home page is `lil.tech`, its privacy policy `lil.tech/privacy`, and `lil.tech` is verified in Search Console (a DNS TXT record on Cloudflare; don't remove it). One iOS-type client for `tech.lil.health` serves the iPhone and the Mac, which share that bundle ID. A **Web application** client serves the agents' authorization page (851-2850, below), with the redirect URIs `https://api.lil.tech/oauth/google/callback` and `https://api.staging.lil.tech/oauth/google/callback`. Its ID is `googleClientIds.web` (`src/auth/Google.ts`), and its secret is `LIL_GOOGLE_WEB_CLIENT_SECRET`: a repo secret that `main.yml` passes to the staging and prod deploys only, kept in 1Password ("lil health – Google web OAuth client (agent sign-in)"), and bound as a Worker secret like the Sign in with Apple key. Staging and prod refuse to deploy without it. Elsewhere it's optional, and without it (or without the client ID) the page has no Google button. The support email is alexandru@851.sh for now: Google only accepts the owner's address or a Google Group they manage, so hello@851.sh would have to become a group.
  - Provider keys are fetched through Cloudflare's cache, and past it at most once a minute (for a new key ID). If they can't be fetched, sign-in answers 503 `SignInUnavailable`, so the app retries.
  - **Each provider ID token signs in once.** Used tokens are recorded (as hashes) until they expire, so a captured sign-in request can't be replayed.
  - **Access tokens:** 15-minute HS256 JWTs carrying the user, device and session. They're verified without a database read, so signing out takes up to 15 minutes to reach them. Each stage has its own signing key, generated and kept by Alchemy.
  - **Refresh tokens:** opaque and random, stored only as SHA-256 hashes. Each one works once: refreshing returns a new pair and revokes the old token. A refresh token expires 90 days after it was issued, so a device that opens the app at least every 90 days stays signed in.
  - **Reuse ends the session.** Presenting an already-used refresh token revokes every token descended from the same sign-in, since only a stolen copy (or a retried request whose response was lost) would do that. The app then signs in again. There's no grace period.
  - **No transactions:** D1 has none over HTTP, so a refresh stores the new token before conditionally revoking the old one. A refresh that fails partway leaves the old token working. Concurrent refreshes, or a refresh racing sign-out, end with the whole family revoked.
  - **Dev sign-in:** previews and personal stages have `POST /v1/auth/dev`, which signs in as a new synthetic user, or to a named one (`account`) that several devices share. That's how previews are checked end to end, since provider sign-in needs real accounts. Staging and prod never register the route. Simulator and Debug Mac builds pointed at a preview offer it on the sign-in screen (the account `e2e`), so the whole sync can be run with synthetic data.
  - Signing out deletes the device's session family. Refreshing deletes the family's expired tokens. Deleting a device or user deletes its sessions.
  - **In the apps** (`LilAuth`):
    - The session lives in the data protection Keychain, readable after first unlock, on this device only.
    - **Each API server has its own session, and dev builds have their own** (851-2974): a build only reads and writes the session for its own server. Every build of lil health on a Mac shares one Keychain access group, Debug and Release alike, and a temporary home doesn't separate them. With a single item, a Debug build pointed at a preview started with the real prod session and sent its tokens to the preview, signing it in replaced the prod session, and signing it out signed the real app out. Prod tokens must never reach staging or a preview.
      - The service is `tech.lil.auth`. Builds that only use prod (Release Mac builds, iPhone builds on a device) keep account `session`, the item every build used before, so they keep their session after updating, with nothing to migrate. Builds that can be pointed at another server (`APIEnvironment.allowsOverride`: the simulator's and Debug Mac builds) use `session` and the server's origin, prod's included, e.g. `session https://api.staging.lil.tech`. So no dev build ever touches the Release app's session.
      - Keyed by what a build can do rather than by Debug or Release: a Debug build installed on an iPhone replaces the App Store or TestFlight one, and must keep its session.
      - A session left by an older Debug build in account `session` (on a dev Mac or a simulator) is read by prod builds as theirs. Prod rejects it and the app signs out, as before.
    - **Each server's local data is its own too** (851-2977): what a build keeps for the signed-in account follows the same split, through `APIEnvironment` (`LilAPI/LocalData.swift`). With per-server sessions but one shared folder, a Debug build opening signed out on a server where it had no session deleted the account data the Release app kept on the same Mac (its health data, which syncs back, and its agent access setting and log, which don't), and switching servers mixed one account's sync cursor with another's rows.
      - Builds that only use prod keep today's places, so nothing moves or migrates: `~/Library/Application Support/tech.lil.health/` (`Health.sqlite`, `AgentAccess.sqlite`), `~/Library/Caches/tech.lil.health/LilSync/` (blobs and snapshot parts), `UserDefaults.standard` (the iPhone's consent and onboarding flags) and the iPhone's `HealthBackfill/` in Application Support.
      - Dev builds keep each server's, prod's included, in a `Servers/<server>` folder inside each of those folders, e.g. `tech.lil.health/Servers/api.staging.lil.tech/` and `Caches/tech.lil.health/Servers/api.staging.lil.tech/LilSync/`, and their settings in a user defaults suite per server, `tech.lil.health.Servers.api.staging.lil.tech` (`keepSettingsPerServer()`, at launch). A suite rather than a key per server, so settings added later are apart too (Sharing also warns about keys with `.`, which observation can't follow). The folder's name is the server's origin, normalized as for the Keychain (lowercased, no default port), without `https://`, and with anything but `a-z0-9.-_` percent-encoded (`http%3A%2F%2Flocalhost%3A8787`), so one server is always one folder and two never share one.
      - `lil-health` picks its server the same way (`LIL_API_URL` in a Debug build), so it reads the folder of the app it forwards that to. A Debug tool talking to an app that's already running must be given the app's `LIL_API_URL`: it can't ask the app which server it uses. Otherwise its request lands in a folder the app doesn't read, and the command times out ("lil health didn't answer") rather than touching another server's data. A Debug tool only looks for a Debug app, and a Release tool for a Release app (below).
      - A dev build's folders sit inside the Release app's, which never lists or removes its folder, only files in it. Signing out of a server deletes only that server's data.
    - **A Debug Mac build has its own bundle ID, `tech.lil.health.debug`** (851-3027), for what AppKit and SwiftUI keep by bundle ID: window frames, the sidebar's width, the Settings window's frame and tab, and the like, in the app's own defaults domain (`UserDefaults.standard`). A dev build writing those into `tech.lil.health` moved and resized the installed app's windows, and a temporary home doesn't redirect user defaults.
      - **Chosen over** frame autosave names per server, which only cover the windows we name, not SwiftUI's split view and Settings keys or ones a later macOS adds, and over redirecting the standard domain, which nothing public does (`-NSUserDefaultsDomain` doesn't exist; arguments only add to `NSArgumentDomain`).
      - **Release builds, and every iPhone build, stay `tech.lil.health`**, so nothing moves for installed apps. A Debug build installed on an iPhone replaces the App Store one and keeps its HealthKit and background task setup.
      - **What follows the bundle ID:** the defaults domain, the per-server suites and the caches folder (`tech.lil.health.debug.Servers.<server>`, `Caches/tech.lil.health.debug/Servers/<server>`), saved window state, privacy permissions, and App Intents: Shortcuts and Spotlight list a registered Debug build as a second lil health, rather than reading its intents as the installed app's. Application Support is spelled out (`HealthDatabase.macDirectory`), so it stays `tech.lil.health/Servers/<server>`, which `lil-health` reads.
      - **What doesn't:** the Keychain access group is spelled out in the entitlements (`$(AppIdentifierPrefix)tech.lil.health`), so a Debug build keeps the per-server items above. Signing uses the team's wildcard development profile, which allows the group; automatic signing fetches it once per Mac (`-allowProvisioningUpdates`, or a build in Xcode). Sign in with Google and Apple's web page don't check the bundle ID, and Sparkle isn't in Debug builds.
      - **Finding the app:** `lil` looks up `tech.lil.health`, so it only ever finds the installed app, never a Debug build in DerivedData. `lil-health` looks for the bundle ID of its own configuration (`HealthCLI.AppConnection`): a Debug tool for a Debug app, which reads the folders it writes to, and a Release tool for a Release app.
    - The `LilAPI` client adds the access token through transport middleware. It refreshes a token a minute before it expires, one refresh at a time. A 401 refreshes and retries the request once.
    - A refresh token the server rejects signs the app out. Other refresh failures (no network, 5xx) keep the session for the next try.
    - Expiry is tracked on the device's clock: the server's times, shifted by how far the device's clock was from the server's when the access token was issued (its `iat`). That way, a clock that's off doesn't make every token look expired.
    - Signing out forgets the session first, then tells the server with the access token it had.
    - The sign-in screen uses the stock Sign in with Apple button, with a Google button under it.
    - **Google without its SDK:** the apps open Google's sign-in page in `ASWebAuthenticationSession`, using the authorization code flow with PKCE. They redirect to the reversed client ID and redeem the code at Google's token endpoint for the ID token. iOS-type clients have no secret. Each app's client ID is `GIDClientID` in its Info.plist (`Apps/LilHealth/<Target>-Info.plist`). Until it's set, the Google button is hidden.
- **Identities and connections are separate:**
  - An identity is a way to sign in. Signing in with Google requests identity scopes only.
  - A connection is a data source the user grants access to, with its own scopes, credentials and sync state: Apple Health now, Gmail, IMAP and calendars later.
- **Account linking:** never automatic by email. A signed-in user links another sign-in method explicitly.
  - **Linking** (851-2554): `POST /v1/me/identities/apple` or `/google` verifies the provider's token as signing in does, and attaches the identity to the signed-in user. An identity that's already theirs is returned unchanged. One that belongs to another user is refused with 409 (`IdentityInUse`), because accounts are never merged. An Apple link keeps Apple's refresh token, as sign-in does.
  - **Unlinking:** `DELETE /v1/me/identities/{id}` removes one in a single guarded statement, so the user's last identity can't go, even when two unlinks race (409, `LastIdentity`). Devices signed in with it stay signed in. An unlinked Apple identity's token is revoked like a deleted account's.
  - **In the apps:** `SignInMethodsSection` (`LilAuth`) lists the linked accounts, with Unlink (unless there's only one) and a Link button for each provider not linked yet, using the sign-in screen's flows. On the Mac it's in the Settings window's Account pane; on the iPhone, a section of the main screen.
- **Deletion and export:** users can delete their account and export their data from inside the apps.
  - **`DELETE /v1/me`** marks the user's store deleted, then deletes their uploaded batch files and blobs, then the user row. Deleting the user cascades to identities, devices, sessions and connections. Every step is idempotent, so a failed deletion can be retried.
    - The store wipes itself and its snapshots from its alarm, logging each step and retrying a failed one a minute later. Wiping a multi-gigabyte store within the request outlasted the iPhone's 60-second timeout (851-2653), and the app then said it was offline. It now reports only real network loss as offline.
  - **Other devices sign out at once** (851-2666): once the account and its sessions are deleted, the store closes its live connections with `4001`, so a signed-in Mac refreshes, fails and signs out within seconds (`docs/sync/protocol.md`). Devices without a live connection (an iPhone) learn at their next request. Apps from before 851-2666 sign out when their token expires, as before.
  - **Stale tokens:** the wiped store stays marked deleted and refuses writes. User IDs are never reused, so an access token that outlives the account (up to 15 minutes) can't write data back, and batches still queued are dropped.
  - **On the iPhone:** Delete Account, with confirmation, then signs out and clears what's local. Health's own data stays.
  - **Exporting data** (851-2596), for GDPR's right to portability:
    - `POST /v1/me/exports` asks the user's store for an export. Asking again within a day gets the same export, so each account builds at most one a day. The store makes a snapshot due at once (still waiting out a bulk upload, at most an hour), and the export is ready once a snapshot covers everything stored when it was asked for. The app polls `GET /v1/me/exports/latest`.
    - A ready export has a signed download URL (15 minutes, like snapshot parts). `GET /v1/exports/download` streams a tar of `README.txt`, `account.json` (profile, sign-in methods, devices, consents, connections without credentials, and connected agents without tokens), `agent-access-log.json` (agents' tool calls, oldest first, read in one store call: at most 10,000 short rows), the snapshot's gzip NDJSON parts under `records/<entity>/`, and the user's blobs under `blobs/`. Nothing is copied or held in memory. The archive's size is known up front, so the download has a `Content-Length`, and a file that's gone fails the stream rather than ending it early.
    - Each file is an R2 call, and a Worker request makes at most 10,000 subrequests, which Alchemy can't raise yet. An account with more than 9,000 files gets 507 `DataExportTooLarge` until exports split into volumes (851-2691).
    - **On the Mac:** the Settings window's Account pane has Export Data, which waits, downloads with progress, then asks where to save the archive.
      - **Without the panel** (851-2894): Export lil health Data (an App Intent, and `lil-health export` later) names a folder instead, since a shortcut or an agent can't answer a panel. `DataExportFeature.exportToFolderRequested` checks the folder first (missing or not writable fails at once, before the server's wait), then exports as the button does, and moves the archive into the folder under the name the panel would suggest (`lil-export-<date>.tar`), numbered as Finder does if it's taken (`lil-export-<date> 2.tar`), never replacing a file; only the server's name's last component is used. The app isn't sandboxed, so it writes where it's told, though macOS still asks before it uses Desktop, Documents or Downloads (a folder chosen in Shortcuts brings its permission, which the intent uses while it waits). Settings shows the same progress, then Saved with Show in Finder.
      - **One export at a time:** an export asked for while one runs, from Settings or another action, fails with "An export is already running." Settings' button is hidden while one runs, and the reducer ignores it too. The server's rule still holds: asking again the same day gets the same export, so a second run that day saves that archive again, under a numbered name.
  - **The Mac's Settings window** (851-2717): a SwiftUI `Settings` scene (⌘, or lil health › Settings…; the sidebar footer's account menu, which also had Sign Out, went in 851-2822, since the app menu had both; Sign Out left the app menu for the Account pane in 851-3096), with a tab per pane: Account, with Sign-In Methods, Your Data and Sign Out…, and Agents. **Sign Out** (851-3096, asked for by Alexandru) is the Account pane's last section, as System Settings' Apple Account pane ends with its Sign Out…, and no longer in the app menu: a button, with a footer saying what signing out does on this Mac (it removes the Mac's copy of the synced data and turns off its command-line and agent access, while the account and the iPhone's data stay), and a confirmation saying the same. The menu item never asked. Who's signed in isn't shown apart from the sign-in methods' emails just above, since the app has no display name without another request. Signing out, from here or because the session ended elsewhere, closes the Settings window and opens the main one, on the sign-in screen: every pane is the account's. A Debug build also signs out when a script asks (AGENTS.md, Without Xcode). It reads the app's store, where the account's state is kept rather than presented, so the window works whether or not the main one is open, and an export keeps going when it closes. The app, not the main window, starts following the session, so that holds while the main window is closed. Signing out cancels what the pane started (`AccountFeature.cancel()`: its sign-in methods' requests and an export, including its save panel's answer) and resets the account; a presented sheet's dismissal used to. Opening the pane again clears a past result (an export saved or failed, a failed link). While the session is being checked, it shows progress; signed out, it says to sign in. It replaced a sheet.
  - **Revoking Sign in with Apple** (851-2612), as Apple requires of apps with account deletion:
    - The apps send Apple's authorization code with the identity token. After signing in, the server redeems it at `appleid.apple.com/auth/token` (for the client ID the identity token was issued to: the App ID or the Services ID) and keeps the refresh token with the identity, encrypted (AES-GCM, with `LIL_TOKEN_KEY`, a random key per stage kept in Alchemy's state). It only keeps a token whose `sub` matches the signed-in identity. A failed redemption never fails the sign-in. That account just can't have its token revoked, until it signs in again. Each sign-in that sends a code replaces the stored token, whichever app it came from. One token per identity is enough while the Services ID stays grouped under the App ID: they're one authorization, so revoking either token ends it, and Apple emails the person "lil health has revoked your Sign in with Apple" (851-2681). If the latest sign-in's redemption failed, the stored token may belong to an authorization that already ended, and the current one isn't revoked.
    - The Mac's web sign-in codes are redeemed with their `redirect_uri` (the API's own `/v1/auth/apple/web`), which Apple requires when the authorization request had one.
    - Deleting an identity (also through its user's cascade) queues its token in `apple_token_revocations`, from a trigger, so the queueing is atomic with the deletion, and a token saved by a concurrent sign-in can't slip through. `DELETE /v1/me` then revokes them at `/auth/revoke`. A failure doesn't fail the deletion. The daily cron tries again an hour later, doubling up to 23 hours (so the next daily run finds it due), for 14 attempts, and drops tokens Apple calls `invalid_grant`. Apple's revoke endpoint answers 200 even for unknown tokens and wrong client secrets, so only a real sign-in proves the setup.
    - Both endpoints need a client secret: an ES256 JWT, valid for 5 minutes, signed with the team's Sign in with Apple key (`J59CSK4YXA`, in 1Password as "lil health – Sign in with Apple key (J59CSK4YXA)"). The deploy reads it from `LIL_APPLE_SIGN_IN_KEY` (the `.p8` PEM; a repo secret in CI) and binds it as a Worker secret. Staging and prod refuse to deploy without it. Elsewhere it's optional, and without it the server skips both calls.
- **Agents (OAuth)** (851-2845): remote agents (Claude, ChatGPT, Claude Code elsewhere) read a user's lil data through an MCP server per app, or every app at once through the combined server (below), after the user allows them with OAuth. The design is in 851-2845, built by its sub-issues (851-2847 to 851-2855), and the combined server's in 851-2846 (851-2899 to 851-2903); the MCP servers are in `server.md`, and what it means for privacy in `health.md` (Privacy, Agents connected to the account).
  - **One authorization server for every lil app,** the API: issuer `https://api.lil.tech` (`https://api.staging.lil.tech`; a preview's or personal stage's workers.dev origin). Ours, in Effect, on D1, not Cloudflare's `workers-oauth-provider`, whose KV storage can't revoke at once or detect refresh token reuse exactly.
  - **A protected resource per app** on the MCP host: `https://mcp.lil.tech/health` (`https://mcp.staging.lil.tech/health`; `<origin>/health` on workers.dev), the URL users paste and its tokens' audience. Its scope is `health:read`, all of the user's lil health data; later apps' scopes keep their prefix (`mail:read`).
  - **Metadata** (851-2847, `src/oauth/`): the authorization server's (RFC 8414) at `/.well-known/oauth-authorization-server` on the API's host, and each app's Protected Resource Metadata (RFC 9728) at `/.well-known/oauth-protected-resource/health` on the MCP host, naming the one authorization server. The root, `/.well-known/oauth-protected-resource`, is the combined server's (below), and there's no OpenID discovery. Prod and staging take both hosts from `stageDomains`, since each document names the other host; on workers.dev both are the request's origin. The MCP host serves only the MCP servers and their metadata, other hosts never serve those, and the authorization server's routes are only on the issuer's host, so not on the Worker's workers.dev URL in prod and staging (404).
  - **Clients are public** (no secrets, `token_endpoint_auth_method: none`), kept in `oauth_clients` in D1, either kind:
    - **Client ID Metadata Documents** first, which Claude and ChatGPT use when the metadata advertises them: the `client_id` is an HTTPS URL, which is fetched and checked. It must be canonical, with a path, not an IP address or a `lil.tech` host (a trailing dot included). The fetch follows no redirects, takes at most 5 s and reads at most 16 KB, and the Worker's `global_fetch_strictly_public` flag keeps it on the public internet. The document's `client_id` must be that URL exactly, with a `client_name` and redirect URIs. It's cached in `oauth_clients` for its `Cache-Control` `max-age`, kept between 5 minutes and 24 hours. Once that expires, a failed fetch refuses the client rather than using the stale copy.
    - **Dynamic client registration** (RFC 7591) second, deprecated by MCP but what MCP Inspector and older clients use: `POST /oauth/register`, at most 8 KB, 10 redirect URIs of at most 2,000 characters, and a `client_name` of at most 100. Only the code flow (`authorization_code`, `refresh_token`). It issues a `cli_…` ID, limited per IP address (`server.md`).
    - **Redirect URIs** (`RedirectUris.ts`, which authorizing and the token endpoint use too): HTTPS, `http` on loopback, or a reverse-DNS private-use scheme, without a fragment. Matched exactly, except that a loopback URI's port is ignored (Claude Code listens on any free port).
    - Both kinds may only ask for the code flow, and every client gets `authorization_code` and `refresh_token`, whatever it asked for (RFC 7591 lets the server replace them), so there's nothing to store.
    - A client without `application_type` is `native` when all its redirect URIs stay on the device, else `web`. Logos are ignored: the consent page loads no remote images.
    - The daily cron deletes clients without a grant: registered ones a day after they were registered or last used (`last_used_at`, set at most hourly when a client is resolved for an authorization), so not one in the middle of an authorization, and any client unused for 90 days. A client with a grant is kept (851-2848).
  - **Grants and tokens** (851-2848, `src/oauth/AgentTokens.ts`, `src/core/AgentGrants.ts`):
    - `agent_authorizations` holds an authorization request for 10 minutes: the client, redirect URI, `state`, PKCE challenge, scopes and `resource` asked for, and the hash of the browser cookie that binds it; once the user signs in, the user; once they allow it, the scopes granted and the code's hash. A code works once, for 60 seconds.
    - `agent_grants` (`agr_…`) is a connected agent: the user (cascading from `users`), the client, its name and domain and the redirect host as the consent page showed them, the scopes and the `resource`: a grant is one app's, or the combined server's (below), whose scopes say which apps. Revoking deletes the row, and its tokens with it.
    - **Tokens are opaque,** 32 random bytes prefixed `lma_` (access, 1 hour) or `lmr_` (refresh, 90 days from when it's issued, so a grant unused for 90 days ends), stored only as SHA-256 hashes in `agent_tokens`. Not JWTs: the MCP servers read the grant on every request anyway, so revoking cuts an agent off at once, rather than when its access token runs out.
    - **The token endpoint** (`POST /oauth/token`, form-encoded, RFC 6749 and OAuth 2.1): `authorization_code` checks PKCE (S256 only; a `plain` challenge never matches), that `client_id` and `redirect_uri` are exactly the authorization's, and that `resource`, if given, is too (else `invalid_target`, RFC 8707). It makes the grant and returns `access_token`, `token_type: Bearer`, `expires_in`, `refresh_token` and `scope` (`health:read`). Redeeming a code again deletes the grant it made, but only from a request that could have redeemed it (the client, redirect URI and verifier), so a used code seen in a log can't disconnect anyone. `refresh_token` rotates on every use, and never changes the grant's scope or resource. Every dead code or token is `invalid_grant`, and responses are `Cache-Control: no-store`. Public clients, so no client authentication, but `client_id` must be the grant's.
    - **Rotation with grace:** the refresh token presented keeps working until the pair it was exchanged for is first used (its access token at an MCP server, or its refresh token here). Claude retries a refresh after 30 s, and the apps' rule of no grace would end the connection whenever a response was lost. Each retry gets a new pair, and the unused pair from the try before is deleted. A refresh token presented after its pair was used is **reuse**, which deletes the grant: only a stolen copy would do that. Each refresh token records the one it `replaces`, and each access token the refresh token issued with it, so finding a used successor is one indexed read.
    - **No transactions over HTTP,** so the order makes it safe, like the apps' refresh. A code is claimed by one guarded update (the grant's ID with it), so only one redemption makes a grant. A second redemption clears the authorization's grant before deleting it, and the first checks after making its grant, so one that ran before the grant existed still ends it. A failure after the claim uses the code up. A refresh records its token's use, stores the new pair, checks for reuse again, counting only pairs issued before its own (one used in between means another party holds the token; a later one is a retry, which may use its pair at once), and only then deletes the earlier unused pair. Two retries of one refresh at once keep the later pair.
    - **`AgentTokens.verify(token, resource)`** is what each MCP server calls with its own resource: it returns the grant (user, client, scopes) or `InvalidAgentToken`, `invalid` or `expired`. A token for another app's server is invalid (the audience check), so a health token can't read mail. It records the grant's `last_used_at` at most every 5 minutes. A tool call (an agent reading) also records the grant's `first_used_at` the first time (851-2872), exactly, with `last_used_at`: `recordFirstUse`, which the MCP route calls once the store answered a request whose method is `tools/call` with a 2xx (a call that errors still counts, like its access log entry; one in a session the store forgot doesn't). Listing tools doesn't count, since agents do that as they connect. The route only decodes the body while the grant has no first use. The apps' access tokens (JWTs with audience `lil`) never pass it, and agents' tokens never pass the API's bearer check, which only takes those JWTs.
    - **Revoking** (`POST /oauth/revoke`, RFC 7009): a refresh token deletes its grant, an access token only itself. It always answers 200, for unknown tokens and another client's (which it ignores) too.
    - **Cleanup:** deleting the account cascades to its grants and tokens. The daily cron deletes expired tokens and authorizations, then grants left with no refresh token that works (after a day, so not one between its writes), then clients without a grant.
  - **The authorization page** (851-2849, `src/oauth/AuthorizationPage.ts`, `AuthorizationPages.ts`): where the agent sends the user's browser, on the issuer's host.
    - **`GET /oauth/authorize` checks the request first.** The client (resolved, so a CIMD document is fetched here) and its `redirect_uri` (matched as registration matches it): a bad one gets an error page, never a redirect, so the page can't be used to send anyone to an arbitrary URL. Then `response_type=code`, an S256 `code_challenge` (`plain` or none is refused) and a `state` of at most 1,000 characters, each refused with a redirect carrying `error`, `state` and `iss` (RFC 9207). A parameter given twice is refused too.
    - **`resource`** must be exactly an app's MCP server URL, as its Protected Resource Metadata gives it, or the combined server's (below) (`invalid_target` otherwise), since the token endpoint compares it as a string. Without one, lil health's server is assumed, as it was when it was the only one, so clients that leave it out keep working; the combined server never is (851-2899). **Scopes** the resource's apps don't have (another app's, unknown ones) are dropped, and none left means all of theirs (`health:read`).
    - **Bound to the browser:** the request is stored in `agent_authorizations` with the SHA-256 of a random cookie, `__Host-lil-agent-auth-<request ID>` (`Secure`, `HttpOnly`, `SameSite=Lax`, 10 minutes, `Path=/`). Every later step needs that cookie, and every form carries a CSRF token, an HMAC of the request's ID keyed by the cookie, so only the browser that started a request can finish it, and nobody can slip their signed-in request into someone else's browser (login CSRF). A cookie per request, rather than one name, lets a browser have two connections going at once (two agents, or one that opened the page twice). Allow and Cancel expire it.
    - **Steps:** the request's page asks to sign in (`POST /oauth/authorize/sign-in`, which records the user on the request), then redirects to `GET /oauth/authorize/consent`, the consent page. `POST /oauth/authorize/decision` takes Allow or Cancel, each once. Allow gives the request the scopes and a code (`lmc_…`, stored as its hash, 60 seconds), then records the app's agents consent (so a request that wasn't allowed has none), and redirects to `redirect_uri` with `code`, `state` and `iss`. The code is an HMAC of the request's ID keyed by the cookie, so Allow sent twice (a double click, whose second answer is the one the browser shows) sends the same code again, until the agent uses it. Cancel deletes the request and redirects with `access_denied`. Nothing is remembered between connections: each one signs in and asks again.
    - **Sign-in:** previews and `alchemy dev` (`devSignInEnvironments`) offer **Sign in to a Test Account**, with the account name (`e2e` by default): the synthetic users of `POST /v1/auth/dev` (`testAccount`), with its 1,000-user cap. Apple and Google can't register previews' changing hosts, so they keep it. Starting a request, signing in and each provider callback count against the `signIn` limit, per IP address (starting one writes a row).
    - **Sign in with Apple and Google** (851-2850): staging and prod (`providerSignInEnvironments`) sign in on Apple's and Google's web pages instead, since the agent's flow runs in a browser, not in our apps. Their buttons follow each brand's guidelines, as in the apps (851-2601): Apple's logo from Apple's own button script, and Google's G and Google Sans (cut down to the label's letters), inline as `data:` URLs, which the CSP allows for images and fonts only. The sign-in form posts `provider`; the server makes a `state` (the request's ID and 32 random bytes) and a nonce, keeps the state's SHA-256 and the nonce with the authorization row (`sign_in_provider`, `sign_in_state_hash`, `sign_in_nonce`; starting again replaces them), and redirects to the provider, sending the nonce's SHA-256 as the apps do.
      - **An answer, then the browser's ticket:** the provider's answer, once checked, only records whose account it was (`sign_in_user_id`) and clears the state and nonce, so it works once. It sends the browser that brought it to `GET /oauth/authorize/signed-in` with a one-time ticket (its hash is `sign_in_ticket_hash`), which signs the account in only with the request's cookie. Otherwise someone could start a request, send its Apple link (with their `state`) to someone else, and get that person's account signed in to their own request: Apple's callback can't check the cookie (below), and the person who signed in has the ticket but not the cookie.
      - **Apple:** the Services ID `tech.lil.health.web` (as the Mac's web sign-in), with the return URL `/oauth/apple/callback` (registered for `api.lil.tech` and `api.staging.lil.tech`), `response_type=code id_token` and `response_mode=form_post`. No scopes (no name or email) and no code redemption: only existing accounts sign in here, so there's no Apple token to keep. Apple's post is cross-site, so the `SameSite=Lax` cookie doesn't come with it: the callback finds the request by `state` alone (refusing posts from another web origin), and finishing (a top-level `GET`, which brings the cookie) checks it. The identity token is checked by `AppleSignIn` and must be the Services ID's.
      - **Google:** the web client, with the authorization code flow, `openid email`, `prompt=select_account`, S256 PKCE and the nonce. Google's answer is a redirect to `/oauth/google/callback`, which brings the cookie, so it's checked there, and the PKCE verifier is derived from it (an HMAC of the request's ID, like the CSRF token) rather than stored. The server redeems the code with the client secret (with a 5-second timeout that aborts the request) and checks the ID token with `GoogleSignIn` for the web client: its tokens must be for it, and the apps' sign-in (`POST /v1/auth/google`, which creates accounts) refuses them.
      - **Existing accounts only:** the identity is looked up in `identities`. An unknown one goes back to the sign-in page with "No lil health account uses this Apple ID (Google account). Set up lil health on your iPhone first." Nothing is created on the web, so the sign-up rules (mainland China's) don't come up. Each ID token is recorded in `identity_token_uses`, as the apps' are, so it signs in once. A token that doesn't check out (or a code Google refuses) says "Signing in didn't work", and an unreachable provider (its keys, or Google's token endpoint timing out or failing with a 5xx) "isn't available right now"; cancelling on the provider's page returns to the sign-in page. A `state` that isn't a waiting request's is an error page.
    - **Consent** names who's asking: the client's name (a registered client's marked **Unverified**, since it named itself), a CIMD client's domain, and the host the browser returns to, with a warning when that's loopback ("this agent is a program on your computer"). Consent is per app: the page names the app (lil health) and says plainly that the agent will read all of its data, read-only, and may send what it reads to its AI provider, with a link to the privacy policy's section on agents (`/privacy#agents`).
    - **The agents consent:** Allow records `agents:health` in `consents`, a type per app (`agents:mail` later) with its own policy version (`agentsConsentPolicyVersions`), separate from Health consent, whose version doesn't change. It's in the data export's `account.json`. Only the consent page gives it; the apps withdraw it (Turn Off Agent Access, below).
    - **Pages:** server-rendered HTML, with no JavaScript or remote resources (lil health's icon is inline SVG), every client-supplied string escaped, and a plain system look in light and dark. Headers: `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; img-src data:; font-src data:; form-action 'self' <the redirect URI's origin>; frame-ancestors 'none'` (the sign-in page's `form-action` adds `https://appleid.apple.com` and `https://accounts.google.com`, for the redirects to them), `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, and no CORS. `form-action` names the agent's origin (or its private-use scheme) as well as `'self'`, because Chrome checks the redirect after a form against it, and `'self'` alone blocks Allow's and Cancel's redirect back to the agent.
  - **The combined server** (851-2846, `src/oauth/Hosts.ts`): one connector for every lil app, `https://mcp.lil.tech` (`https://mcp.staging.lil.tech`; the origin on workers.dev), another protected resource on the one authorization server. Each app's own server stays. Built in four steps, one design: authorizing it (851-2899, here), the MCP server at `/` (851-2900, `server.md`), its grants in the apps' API and Turn Off (851-2901) and in both apps' Settings (851-2902); then the policy, the help page and prod (851-2903).
    - **Canonical without a trailing slash,** as MCP's server URIs are. `https://mcp.lil.tech/` is the same resource at `/oauth/authorize` and `/oauth/token` (clients that parse the URL add the slash), and is stored without it. Nothing else is: `//`, a query or a path is another resource.
    - **Metadata** at the MCP host's root, `/.well-known/oauth-protected-resource`: `resource`, the one authorization server, every app's scopes, `resource_name: "lil"` and the help page. `/` and that document are the MCP host's (`isMcpPath`), as exact paths. The authorization server's metadata lists every app's scopes too.
    - **The scopes asked for choose the apps:** unknown scopes are dropped, and none at all means every app's. The grant's scopes are those apps' scopes.
    - **Consent** names "lil" and lists each app the request covers, with its icon: "<Agent> will be able to read all of your data in these lil apps: lil health." Allow records each listed app's agents consent (`agents:health`, later `agents:mail`), against that app's policy version, as an app's own page does.
    - **All or nothing:** the page has no choice of apps. The agent's scopes already chose them, so the page is one decision about what it asked for, and the agent gets all of it or nothing (a narrower grant than asked is something clients handle unevenly). An agent that should read only one app connects to that app's own server, and the page says so.
    - **Tokens:** the grant's `resource` is the combined server's URL, so `AgentTokens.verify` (the audience check) accepts its tokens only there: a combined token is refused at `/health`, and an app's token at the combined server. Refresh and revoke are unchanged.
    - **The registry:** everything is derived from the apps in `agentResources`, so a later app joins the combined server by being there. The authorization page and metadata read it through the `AgentApps` reference, which tests replace with a fake second app (lil mail) to check two apps listed, two consents recorded, and `mail:read` alone listing only mail.
    - **Gate:** its own, `combinedAgentEnvironments`, a subset of `agentAccessEnvironments`: `preview`, `local` and `staging` while it was built, and `prod` since its launch (851-2903), once the privacy policy described it (`health.md`, Privacy), both apps listed and revoked its agents (the Mac and iPhone releases with 851-2902, lil health 0.3.0), and lil.tech/agents explained it. Where it's not allowed, its metadata and `/` are a 404, and asking for it at `/oauth/authorize` is `invalid_target`.
    - **The server** at `/` is 851-2900's (`server.md`, MCP servers). It serves only the apps whose scopes the grant still has, less any whose agents consent was withdrawn since the grant was made: one consent read per request, a second check behind Turn Off taking the app's scopes away (851-2901, below).
    - **In the apps** (851-2901, 851-2902): a combined grant is listed with `app: null` and the apps it reads in `apps`, in every app it reads, with an **All lil apps** label. An app's Turn Off Agent Access takes that app away from it (below), and revoking it deletes the whole grant, so it loses every app. This is what the privacy policy says (`health.md`).
  - **In the apps** (851-2852, `src/oauth/AgentsApi.ts`): what the apps can see and revoke, through the OpenAPI spec like the rest of their API, with the app's access token and the `user` rate limit. Agents' tokens never reach these routes. They exist in every environment, prod included, so the apps could ship before agents could connect there (prod since 851-2855).
    - **`GET /v1/me/agents`** lists the account's grants that still work (a refresh token that hasn't expired; ended ones wait unlisted for the daily cleanup), for every app, most recently connected first: `id` (`agr_…`), `name` (`null` for a registered client that gave none), `domain` (a CIMD client's, `null` for an unverified registered one), `redirectHost`, `resource` (the app's MCP server URL), `app` (`health`, from the resource's path, since an app's requests can come to another origin than its agents' under `alchemy dev`; `null` for a server the deployment doesn't know), `connectedAt`, `lastUsedAt` (recorded at most every 5 minutes, and at the first tool call, so the connection time until then) and `firstUsedAt` (the first tool call, exact; `null` until the agent reads anything, which the apps show as "Not used yet"). `apps` (851-2901): the apps it can read now, from its scopes: `["health"]` for lil health's own server, and for the combined server each app it still holds a scope of (its `app` is `null`). A required list of strings, added rather than changing `app`, so installed apps keep working and just don't show combined agents until they read it (851-2902); strings, not an enum, so later apps don't break them. It's from the scopes alone, without the consent read the MCP server does, since Turn Off takes an app's scopes away. The export's `account.json` has it too. `firstUsedAt` was added later (851-2872) rather than making `lastUsedAt` nullable, which would break installed clients. It wasn't backfilled: only previews had grants then (staging's page has no sign-in), and `last_used_at` can't tell a read from listing tools. `resource` and `app` are strings, not enums, so later apps don't break installed clients; each app shows those whose `apps` name it (installed ones, those whose `app` is its own).
    - **`DELETE /v1/me/agents/{id}`** revokes one: it deletes the grant (only the user's own), and its tokens with it, so its next MCP request gets 401 and its refresh token `invalid_grant`. It answers 204 whether or not there was one, so it's idempotent and says nothing about other accounts' grants.
    - **`GET /v1/me/agents/access-log?before=…`** reads the user's store's `agent_access_log`, newest first, 100 a page, with `nextBefore` for the next page (`null` on the last). An entry's `id` is its row's, which only grows, so pages never skip or repeat a row; time could. Each entry has `at`, `agentId` and `agentName` (the grant and its name when it called, or its client ID if it gave none, kept after the grant is revoked), `tool`, `types`, `range`, `date`, `outcome` (`ok`, `error`, `too_large`, a string) and `rows`. Never values. It's every app's log in one, since the log doesn't record the server (only Health has one); an app can filter by `agentId` while its agents are connected.
    - **`GET /v1/me/consents/agents/health`** is lil health's agents consent in force (`given`: its policy version and time, or `null`). **`DELETE`** is **Turn Off Agent Access**: it deletes lil health's authorization requests, then its grants (those whose resource's path is `/health`), then withdraws `agents:health`, then deletes them again. Combined grants (851-2901) lose the app's scopes instead, in the same passes: first their requests that asked for any of them are deleted (as above, so an allowed code can't make a grant; one whose grant already exists stays, so the code's reuse still ends that grant), then the scopes are taken out of each grant (one guarded `UPDATE` over its JSON array), then grants left with none are deleted, with their tokens. A combined agent that reads other apps keeps them, and its next request sees the narrower scope, since every MCP request reads its grant; a refresh answers with the grant's current `scope`. Because the server does it, an installed app's Turn Off covers combined grants before it shows them. A code redeemed during Turn Off that asked for the app is still deleted whole, other apps and all, since the request it came from is gone. Revoking first means a failure leaves consent standing and the app retries, rather than agents reading without it. Deleting the requests before the grants means a code allowed just before can't make a grant after: redeeming it finds its request gone and deletes the grant it made. The second pass catches an agent allowed in a browser while the first ran; one allowed after it gives consent again, as a new connection. Other apps' grants and consents, and Health consent, stay. Later apps get `/v1/me/consents/agents/mail` and so on: a nested path, since a colon in a path reads as a parameter to routers.
    - **Account deletion** cascades to grants, and the store's wipe takes the log.
    - **On the Mac** (851-2853): Settings › Agents, below the local command-line access, lists lil health's agents (those whose `apps` contain `health`, 851-2902) with their domain (or Unverified, for one that registered itself), when they connected and last read, and Revoke…; Turn Off Agent Access…; the MCP server's URL to copy (`APIEnvironment.mcpURL(app:)`, so staging and previews show their own; hidden in prod until the launch, 851-2855, which removed `servesAgents`); How to Connect an Agent under it; and the remote access log, a page at a time, in a sheet opened from a row under the agents (851-3082, `health.md`). Both ask first. It reads them again each time the pane opens; the state is in the app's store, and signing out cancels and resets it. The client is `ConnectedAgentsClient` in `LilAuth`.
    - **On the iPhone** (851-2854): Settings › Connected Agents, a screen of its own: the same agents, each revoked with a swipe; Recent Access, the log on a screen of its own, its next page loaded at the end of the list (or Show More); the MCP server's URL to copy, with How to Connect an Agent; and Turn Off Agent Access. Both apps' How to Connect an Agent opens the help page, [lil.tech/agents](https://lil.tech/agents) (851-2855, 851-2877): `APIEnvironment.agentsHelpURL`, `staging.lil.tech/agents` on staging, as the API's `resource_documentation` links it. The feature, `ConnectedAgentsFeature`, moved from the Mac's app to `LilAuth` for it, and both apps show its state with their own views. Its state is with the Settings sheet's (`SyncStatusFeature`), so signing out resets it, and cancels its requests.
    - **Combined agents in both apps** (851-2902): an agent connected through the combined server (`app` is `null`, `ConnectedAgent.isCombined`) is listed while its `apps` contain the app's own key, with a short **All lil apps** label next to its name (after Unverified, when it's that too). Revoking deletes the whole grant, so its confirmation says so: "Revoking it disconnects it from every lil app it's connected to, at once." (the privacy policy's "Revoking an agent connected this way disconnects it from all of them"). A label rather than the list of apps it reads: with one app there's nothing else to name. Like Turn Off's copy, revisit it once a second app exists, since a combined agent whose other app was turned off no longer reads all of them. Turn Off Agent Access's copy stays the same, since with one app a combined agent ends just like a per-app one; revisit it once a second app exists, when a combined agent keeps reading the others. The URL to copy stays lil health's own server, since this is lil health's Settings; lil.tech/agents explains the combined one. Installed versions before this don't list combined agents, but their Turn Off still covers them (851-2901), so the Mac and iPhone releases with it (lil health 0.3.0, build 319, 851-2944) shipped before the combined server reached prod (851-2903).
  - **The MCP servers** check every request's token against their own resource and read its grant, so a revoked grant gets 401 on its next request (851-2851, `server.md`).
  - **CORS:** any origin, without credentials, on the metadata documents, `/oauth/register`, `/oauth/token` and `/oauth/revoke`, with preflights, for browser-based clients such as MCP Inspector. None use cookies. Not on the authorization page, which does, or the apps' API.
  - **Previews and staging first, then prod:** the routes exist only in `agentAccessEnvironments`. That was `preview`, `local` and `staging` until the launch (851-2855) added `prod`, once the privacy policy described agents (`health.md`, Privacy) and both apps could revoke them. A new environment opts in there. The combined server followed the same path behind `combinedAgentEnvironments`, reaching prod with 851-2903. They follow their own RFCs, so they're left out of the OpenAPI spec, like `/v1/auth/dev`.
