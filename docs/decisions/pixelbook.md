- **Published from the state catalogs** (851-2955, 2026-10-22): Pixelbook shows the catalogs' committed references, published by CI from git, and renders nothing. Until then it rendered every `#Preview` itself (851-2697): [SnapshotPreviews](https://github.com/getsentry/SnapshotPreviews) through our fork, [851-labs/SnapshotPreviews](https://github.com/851-labs/SnapshotPreviews), in a project of its own (`Tools/PixelbookSnapshots`), with Mac previews that filled a window captured from the screen (ScreenCaptureKit, which needed Xcode's Screen Recording access), before every push (`scripts/pixelbook render`). That was paused on 2026-10-20 (851-2816): the iPhone simulator kept hanging or failing renders (a run once hung silently for 47 minutes), and with several worktrees and agents on one Mac, the render lock (851-2805) queued work for 30+ minutes. 851-2948 replaced it with state catalogs in snapshot tests, and once every screen had one, 851-2969 removed the renderer, the fork (archived on GitHub, not deleted, 851-2948's decision 5) and its tickets (851-2814, 851-2767, 851-2769, 851-2809). Git history before 851-2969 has this file's account of it: the fork's window capture, scroll expansion, fixed clock and framework signing.
- **Snapshot tests** (851-2931): swift-snapshot-testing renders Mac preview states in `swift test` (`HealthSnapshotTests`, AGENTS.md), offscreen with `CALayer.render(in:)` at 2x, with no Xcode, Screen Recording or render lock. Six states took 0.1–0.3 s each, and matched pixel for pixel across 16 runs (two of them at once) and between a Retina MacBook and a mini's 1x display over SSH. They match `RenderPreview` except Liquid Glass, which only draws on screen. They're the start of developing without Xcode open (851-2948), and what Pixelbook publishes. iPhone snapshots need the simulator (below): they rendered the same way in a hostless test, but `xcodebuild` took 30 s to 9 minutes to start the runner.
  - **A fixed "now", calendar, locale and database** (851-2950), so state catalogs' images only change when the UI does, with no clock hook (the old renderer's went with it, 851-2969). `HealthDatabase` has `previewNow` (Tuesday, August 13, 2024, 3 PM in Los Angeles: the old renderer's day, but the afternoon, since its 07:00 UTC is midnight there and leaves today without data), `previewCalendar` (Gregorian, Los Angeles, `en_US`) and `catalogDatabase`, the preview data built from them once per process. Catalogs pass `previewNow` and `previewCalendar` to whatever asks for the date, and a catalog's suite makes the database, date, calendar, time zone and locale dependencies theirs (`.dependencies { … }`). `fixTimeZoneAndLocale()` (`HealthSnapshotTests`, called first by the suite's trait, which runs before its `init`) makes the calendar's time zone and locale the test process's, with the Mac's format settings (24-hour time, first weekday, units) overridden in the process's argument domain, as `-AppleLocale` does: text a view formats itself (`formatted()`) follows the process's locale, not the environment's, and came out in French under a French one. `Locale.current` is read once, so a test fails if anything read it before. Every state rendered the same with `-AppleLocale de_DE -AppleICUForce24HourTime YES` and with `-AppleLocale fr_FR -AppleMetricUnits YES` on the command line, and "Steps, week" failed without the fix. `makePreviewHealthDatabase(now:calendar:)` takes both from its caller: without them, it took the `date` and `calendar` dependencies, the wall clock in previews, until 851-2970 deleted the last previews.
  - **State catalogs** (851-2949): a screen's states move from `#Preview`s into a catalog in the test target (`StateCatalog`, AppKit-free so the iPhone and lil messages can share it), and its previews are deleted. One parameterized test per catalog snapshots every state in light and dark, at the state's width and at least its height, growing to its content. A state records its `#fileID` and `#line`, for failures and Pixelbook's source links (851-2955). Graphs name a catalog's file and its states. References are all committed (Alexandru, 851-2948): Metric Detail's 17 states are 34 images, 3.3 MB, 43–120 KB each (96 KB on average), and its test takes about 10 s on a loaded laptop.
    - **Manifests** (851-2955): a catalog's test also writes its screen's manifest beside its references, `__Snapshots__/<Catalog>/<screen>.json` (`CatalogManifest` in `StateCatalog.swift`): the app (`pixelbookApp`, the test target's), the screen, the catalog as graphs name it (`Module/File.swift`), and each state's name, ID (`<screen>.<state>` slugs), source file and light and dark references, from the repository's root. A catalog can't be read without running it: `SignInCatalog` shares states between the Mac and the iPhone, under a different screen on each, and adds one on the Mac only, behind `#if os`. The test writes the manifest when it's missing or differs, once per screen and process from the whole catalog (so a filtered run writes all of it), and fails unless it's recording, as SnapshotTesting does with a missing reference. A test can't see a manifest it no longer writes, and the iPhone's only run after merging, so the graph check (`manifestProblems` in `graphs.ts`, before every commit that touches catalogs) also fails on a manifest whose catalog file is gone or whose screen isn't in it any more (renamed), a state it has that its file doesn't, a missing reference, and a `CatalogState("…")` in a catalog file that no manifest has. Lines aren't in it, so editing a catalog doesn't make it stale (the iPhone's tests only run after merging): publishing finds each state's `CatalogState("…")` line in its file.
  - **Within 1 per color channel** (851-2985): an image matches its reference when every pixel's channels (alpha included) are at most 1 apart, and fails on any pixel further apart, or a different size (`snapshotChannelTolerance`, `HealthSnapshotTests/MacSnapshot.swift`). References recorded on a laptop on macOS 27.0.1 (26A434) failed on the minis' 27.0 (26A428) exactly that far apart: 851-2952's and 851-2964's 14 failed images had 30 to 6,370 pixels changed (an avatar's `.gray.gradient`, the toolbar search field, SF Symbols), every one by exactly 1, and looked identical. A real change is much further apart: a workout map that changed on the minis the same day had 835,016 pixels changed by up to 222. Moving anything with an edge (text, a symbol, a border) by a pixel, or recoloring by 2 levels or more, fails, which `SnapshotToleranceTests.swift` checks on made-up images. What passes can't be seen: a smooth gradient or soft shadow moved a pixel (its neighbors are 1 apart), a nearly transparent pixel's change, or a color 1 level off. `perceptualPrecision` was the alternative: a color difference (ΔE) per pixel, measured by Core Image. 0.98, the usual choice, allows ΔE 2, which is 4 or 5 levels of gray and more in some hues, so it would pass a slightly retinted background, while a 1-level change is ΔE 0.35–0.45 in grays. A fixed limit on channels is easier to reason about, and the same in every hue. `scripts/snapshot`'s diff marks only pixels beyond the limit, and says by how much they differ and how many more differ within it.
  - **Whole windows** (851-2952): `WindowCatalog` snapshots `AppView` in its states. A snapshot test holds the main queue (a main-actor test runs on it) until the image is taken, so nothing a view starts asynchronously arrives: no `.task` runs, and a `@Fetch`'s first value, which `MainQueueScheduler` delivers on the main queue, never comes. Deterministic, but a category came out blank. So the window's test sets `fetchesFirstValueAtOnce` (a `HealthDatabase` dependency, off in the app), which makes `MainQueueScheduler`s fetch the first value on the spot, and its pages show their data; pages that load in a `.task` (a metric's chart, Sleep's nights) show as loading, as a preview's first frame did. Requests read the date and calendar from dependencies inside `fetch`, which SQLiteData runs with the dependencies of where the fetch started. The sidebar floats in Liquid Glass on macOS 26, so it doesn't draw offscreen, rows, search field and sync footer included (851-2957); the footer has its own catalog.
  - **lil messages' catalogs** (851-2968): `MessagesSnapshotTests`, a SwiftPM test target of its own, so lil health's tests don't build lil messages, and its catalogs get their own fixtures (the synthetic `chat.db`, contact names and photo). Its snapshot support is `HealthSnapshotTests`' files (`StateCatalog`, `MacSnapshot`, `SnapshotOutput`, `SnapshotEnvironment`), linked with symlinks, as the iPhone's project builds them, rather than a support module, whose types would all have to be public. `SnapshotEnvironment` takes its calendar from the target (`snapshotCalendar`). It has the same fixed "now" and calendar as lil health's, with `makePreviewChatDatabase(now:calendar:)` built from them once (`catalogChatDatabase`). Stores have no reducer (`EmptyReducer`): offscreen, the conversation list's `.task` did run before the image, and replaced an empty list's state with loading.   - **Laid out and drawn at 2x, whatever came before** (851-2986, 851-3010). Snapshots flaked in two ways, and neither could be made to happen on purpose: 1,200 renders of the failed states in one process all matched.
    - **Under load on a laptop,** about one image in 400 (load 180–500). `NSWindow(contentViewController:)` has SwiftUI lay the view out before it's in the window, at its default 1x, then at the window's 2x. Blood Pressure's legend dot came out half a point up (851-2987), pixel for pixel where a 1x layout puts it. Some text was blurred, and pages taller than about 2,870 pt had a band drawn from another part of the page.
    - **On the minis, every run.** Their displays are 1x, and one title came out blurred, with a dark halo in dark mode. Which title depended on how many snapshots ran before: Window "Summary", Symptoms "Headache, day", Settings "Agents: on, empty log" (851-3010).
    - **The cause of the blur:** a dump of the layers of a blurred image, caught in a full run, showed the blurred text's `CGDrawingLayer` (SwiftUI's text and shapes) at `contentsScale` 1, with contents drawn at 1x, where every other one was at 2x. SwiftUI draws the view before it's in its 2x window, at 1x, and now and then a layer kept that drawing.
    - **The fix:** `assertMacSnapshot` gives its view `.environment(\.displayScale, 2)`, so every layout pass rounds as 2x does. Right before rendering, `layerImage` draws again at 2x every layer that draws its own contents: SwiftUI's `CGDrawingLayer`s, and any with a `CABackingStore` (`redrawAtSnapshotScale`). `render(in:)` draws each layer's contents as they are, so the image no longer depends on what scale a layer was last drawn at. Correct images come out byte for byte the same, and `layersDrawnAt1xAreDrawnAgainAt2x` checks a layer left at 1x. Layers whose contents were set rather than drawn (images) are left alone: drawing them again would clear them. `snapshotScale` is the one place that says 2x.
    - **Dropped:** putting the view into a window that was already 2x, and already its size. That also removed the 1x pass, but AppKit then laid the window's toolbar out at the screen's scale, and on the minis' 1x displays the range picker's labels came out 1 to 2 px apart.
    - Symptoms' and All Data's long states grow to their content again (up to 13,915 pt, All Data's long day: a 1,120 × 27,830 px, 2.8 MB reference).
  - **No wallpaper tinting** (851-3172, 2026-10-23): the test process turns off "Allow wallpaper tinting in windows", as `-AppleReduceDesktopTinting YES` would (`AppleReduceDesktopTinting`, set with the locale's settings in the argument domain by `fixTimeZoneAndLocale()`, `SnapshotEnvironment.swift`, which each suite's trait calls before anything draws, since AppKit reads it once). Offscreen windows never take the tint, but views Swift Charts draws do: with the setting on, a sparkline's hollow latest dot (851-3101), filled with `.background.secondary`, came out gray 58 where the same fill outside a chart is 42, in dark mode only. The references had been recorded untinted; once the laptop rendered with the tint (its setting is on), 12 dark Category, Summary and Window images failed by up to 16 per channel, consistently, on the dot's inside alone, and two images recorded afterwards (851-3116's Body Measurements) had the tint in them. GPU load, drawing order and the date had nothing to do with it: a standalone render gave 58 with the Mac's setting and 42 with `-AppleReduceDesktopTinting YES`. `chartsDrawTheBackgroundWithoutTheWallpapersTint` (both Mac snapshot targets) checks it, but can only fail on a Mac with tinting on. The images are what an untinted window shows; a real window's tint is checked in a real window, as Liquid Glass is.
  - **Stale toolbar images drawn again** (851-3230, 2026-10-23): once CI compared every image (851-3070), Sleep › Week (light) failed in about one full Mac run in four on either mini, always the same 171 pixels of the toolbar's ‹, by up to 45, and passed on a re-run. A dump of the title bar's layers in a failing run showed the chevron's SwiftUI `ImageLayer` holding a 13 × 23 px bitmap in an 8.5 × 14.5 pt layer, where every good render has 17 × 29: a toolbar item's symbol is drawn first at the size it has before the toolbar sizes it (in `NSWindow(contentViewController:)`, as the item's hosting view joins the window), then again as the window places itself and lays the toolbar out; logging every `contents` set showed that second drawing skipping the ‹ in the failing runs, and nothing drew it again, 0.3 s later or after laying the window out again, since SwiftUI's display list hadn't changed. It only happened after the catalogs before Sleep (never in 8 runs of Sleep's catalog alone, or 6 passes of it in one process), and never on a laptop; layout and animation settling, glass, fractional geometry and the chevron's enabled state had nothing to do with it. `snapshotWindow` now finds title bar images whose bitmap isn't their layer's size at its scale (`staleToolbarImages`: toolbar images are symbols, drawn to fit) and has their hosting views go to the other appearance and back, which changes the display list, so SwiftUI draws them at their final size, byte for byte as when nothing was skipped, and prints that it did. Changing the whole window's appearance instead drew the window's title differently afterwards. Settling longer wouldn't have helped (a stale bitmap stays stale), rendering a differing state again in a fresh window would only have hidden it, and the tolerance stays. `staleToolbarImagesAreDrawnAgain` checks it on a made-up stale bitmap.
  - **iPhone catalogs** (851-2953): run in the iPhone 18 Pro simulator, hosted by an empty app (`PhoneSnapshotHost`), and drawn through the window server (`drawHierarchyInKeyWindow`), so Liquid Glass renders (swift-snapshot-testing issues #1029 and #1019); 851-2931's hostless spike drew the glass Settings button nearly invisible. `scripts/snapshot --iphone` runs them.

The window rather than the state's view (851-2967), so an alert it presents is in the image; the old renderer's iPhone snapshots never showed alerts. An alert takes the window's style, not its presenter's, so a presented controller is given the state's and 0.3 s more to settle. Every animation in the state's own layers is removed before drawing, so spinners and indeterminate bars draw at rest: frozen instead (`layer.speed = 0`), a spinner came out at a different step in each run.
    - **Within 2 per color channel**, where the Mac's are within 1 (851-2985): even so, the glass Settings button's rim came out 1 or 2 apart in a channel, in about one image in ten (68–141 pixels, nothing else changed): the window server's rounding, not the view (`phoneChannelTolerance`, `PhoneSnapshot.swift`). SnapshotTesting's perceptual tolerance (`perceptualPrecision: 0.97`) passed too, but per channel is the Mac's rule, and stricter.
    - **The status bar** is the system's, so it isn't in the images; the safe area is.
    - **The screen's height** (851-2967): a state fills the screen, as the app shows it, where the old renderer grew an iPhone preview to its scroll content. What scrolls below (the rest of Settings, a long log) isn't in the image, and no scroll edge effect needs hiding (851-2716), since nothing is expanded. Each state's controller is dismissed and removed, and the run loop turned once, before the test ends, and the iPhone's Connected Agents reads the date where the catalog makes it and passes it to its rows.
    - **Shared with the Mac** (851-2967): the sign-in screens, which both apps show, have one catalog each in `HealthSnapshotTests/Catalogs/LilAuth`, which the iPhone's target builds by reference, so Pixelbook's graphs name one file for both apps. Each target renders it as its app does (`#if os(macOS)`), with the platform in the screen's name (`Sign In (Mac)`, `Sign In (iPhone)`), since both platforms' references share its `__Snapshots__` folder. A Mac-only state is added under `#if os(macOS)`. The iPhone's branch is `#elseif PHONE_SNAPSHOT_TESTS`, a condition only that target sets, so the package's test target still builds for iOS. Each such file is a file reference in the iPhone's project (its synchronized folder is `HealthPhoneSnapshotTests` only), and the folder's `__Snapshots__` an `exclude` in `Package.swift`.
    - **CI:** after every merge to `main` that touches Swift, on a mini (`iphone-snapshots` in `swift-check.yml`), in a simulator of the job's own that it deletes. Pull requests too since 851-3070, when they touch what the iPhone's tests are built from (`iphone` in `.github/actions/changes`: the package modules `PhoneSnapshots.xcodeproj` links, with their dependencies, the shared catalogs and support files, the package's manifest and pins). About 3 minutes on a mini, beside `check`, where 851-2948's decision 4 had kept it off pull requests for a cold simulator's minutes; most pull requests (the Mac's pages) don't touch it. `scripts/check-iphone-paths`, in `scripts/check --swift`, fails when a module the tests are built from isn't covered, so a new dependency can't slip past.   - **CI rendered without comparing, for a day** (851-3071, Alexandru, 2026-10-22): references recorded on a laptop (M1 Pro) didn't match the minis' (M6) renders, on the same macOS 27.0.1 (26A434): 851-3033's Sleep apnea notifications came out up to 2 apart in a channel, all inside the `lungs.fill` symbol, so the GPU, not macOS. Raising the tolerance (which would pass real 2-level changes) and hand-editing references were both turned down.   - **CI renders the references** (851-3070, P0, 2026-10-23): without CI comparing, agents ran the whole Mac suite (~770 images, 6–9 minutes of a laptop's CPU) several times per ticket to catch stale references in the catalogs that embed other views (851-3108), which drained the laptop with agents in parallel. Now the Mac minis render every reference, Mac and iPhone, compare every image on every pull request, and laptops never record or run the whole suite.
    - **Measured:** both minis (tamale and croissant: M6, macOS 27.0.1, Xcode 27.1) rendered all 834 Mac images byte for byte the same, so comparisons aren't pinned to one. Against the laptop's references (M1 Pro, the same macOS), the minis drew 816 the same, 16 at most 1 apart and 2 (Sleep apnea notifications' lungs) 2 apart; of 160 iPhone images, 113 the same and the rest at most 2 apart, the glass rim's existing tolerance. So the minis' references were recorded once, from those runs (the images that differed at all), and CI keeps its tolerances: the Mac's within 1, the iPhone's within 2.
    - **On CI** (`LIL_SNAPSHOT_CI=1`, `snapshotsRenderReferences`): images are compared, and a state with no reference is recorded into the checkout, and fails, as SnapshotTesting does. A failed check runs `scripts/collect-snapshots`, which gathers each image that differs (the run's render) and each reference or manifest the tests wrote, at their paths in the repository, into the `snapshot-references` artifact (`iphone-snapshot-references`), the same images with their diffs into `snapshot-changes`, and writes a job summary listing them, with an error annotation saying how to update them. 14 days' retention.
    - **Updating references:** `scripts/fetch-snapshots` (in the branch, after the push) finds the PR's run for the commit checked out, waits for it, downloads those artifacts and copies only files at reference and manifest paths into the branch, then makes the before/after sheet of them (`scripts/snapshot-sheet`, from a report it writes in `LilPackage/.build/snapshots-ci`). Someone looks at them, commits and pushes; the check passes, and Pixelbook's comment links the comparison. A UI change takes two CI runs, the first to render.
    - **Not a bot commit:** CI could commit the images to the branch itself (on a label or comment), but a push with the workflow's `GITHUB_TOKEN` starts no workflow, so the new head would never get `pr-ok`; a GitHub App's token would, at the cost of a secret with write access on the minis' jobs. Fetching keeps CI read-only, and the person or agent who made the change looks at the images before committing them. Approving in Pixelbook, which needs that token, is a follow-up.
    - **Off CI** (a laptop): the Mac's images match within 2 (`laptopChannelTolerance`), which covers every image measured, so a difference is the change being made; a comparison there is only an early warning. A new state is only rendered (`new`, `isNewOffCI`), without failing or writing a reference. `scripts/snapshot --record` refuses, and the pre-commit hook's manifest check only warns on a missing reference (`graphs.ts --allow-missing-references`), since a new state's come after the push. The Swift check's still fails on one.
    - **Kept in git:** the references stay committed, read by Pixelbook from git (851-2955). Moving them out (the ticket's first direction) would change publishing, keys and the local loop for no gain in comparing, which is what was urgent.
- **Publishing** (851-2699, 851-2955): `scripts/pixelbook publish [--commit <sha>] [--ref <name>]` uploads a commit's state catalog images to the R2 bucket `lil-pixelbook`, public at `pixelbook-assets.lil.tech` (read-only, CORS open), which every stage's Pixelbook reads. Only prod's stack creates it, since there's one set of snapshots.
  - **From git, not a render:** the uploader (`Services/api/scripts/pixelbook.ts`) lists the commit's `LilPackage/Tests` (`git ls-tree`), reads every catalog manifest, its states' sources and its references as blobs, and builds each app's manifest from them. So any fetched commit can be published, with no Xcode, simulator, Screen Recording or lock, on Linux, and the working tree doesn't count. A manifest whose catalog file is gone, or a state without a reference, is left out with a warning (`::warning::` on GitHub). Every screen is in a catalog (lil messages since 851-2968).
  - **Keyed by inputs, not commits:** a key is a hash of the git trees snapshots come from: every test target's `Catalogs` folder (sources, references and manifests), `scripts/pixelbook` and the uploader. A squash merge makes a new commit, but its trees match the branch's, so main finds the branch's snapshots, and a commit that changes no catalog shares its parent's.
  - **Layout:** `images/<sha256 of the PNG>.png`, each stored once, so an unchanged screen isn't uploaded again. A reference's bytes only change when it's recorded again, so they're hashed rather than its pixels (renders' PNG metadata differed run to run; references are committed). `snapshots/<key>/<app>.json` is an app's manifest (screen, state, catalog module and file, the state's source path, line and place in its catalog, and each appearance's image, size and scale), and `snapshots/<key>/index.json`, written last, marks a key complete. `commits/<sha>.json` and `refs/<branch>.json` point at keys.
  - **Snapshot IDs** are `<screen>.<state>` slugs, which name the references, so renaming a screen or state is one removed and one new, and moving a catalog changes nothing. A comparison across the switch from previews shows every screen removed and new, once.
  - **Source links** use the state's file (`path`) and line: its `CatalogState("…")`, found by name in the file at that commit, as `#line` gives it. Previews' manifests (851-2790) had the preview's file, found under `LilPackage/Sources/<module>`, as modules were before the product folders (851-3065).
  - **States in their catalog's order** (`order`), not their lines', since shared states can be written after a platform's own.
  - **Thumbnails** (851-2712): `thumbnails/<the same sha256>.png` is each image at a quarter of its width and height, and the manifest names it. Zoomed out, the canvas would otherwise load and decode every snapshot at full size (about 100 MB at Fit), so tiles use thumbnails while they'd hold at most half a screen pixel per point, which a quarter-size Mac (2x) image still has; the detail panel always shows the original. Made in Node (`Services/api/scripts/png.ts`: zlib, a box filter weighted by alpha, Paeth rows), since CI's Linux has no `sips`: about 90 ms an image, 22 KB on average. PNG, for transparency.
  - **Skipping work:** a published key is only pointed at: `publish` writes the commit's and ref's pointers, and only those that changed. A second run uploads nothing.
    - A branch's pointer doesn't move back to an older commit (a re-run of an earlier merge's job), unless `--force-ref` (a PR's push, which is the branch even when it rewinds).
  - **When:** in CI, which has the deploy token: `pr.yml`'s `pixelbook` job publishes each PR's head (and points the branch at it), and `main.yml`'s publishes each merge and points main at it, in order. A PR doesn't publish its base: it would be published with the PR's copy of the uploader under a key made from the base's, and a key with an index is never published again, so a PR changing the uploader could fill main's keys with its own output. Each commit is published by its own scripts, which are in its key. Nothing runs before a push any more; lefthook's pre-push hook (851-2703) rendered and published there, on the developer's Mac, until it was paused. Publish by hand with `scripts/pixelbook publish`, which needs a Cloudflare login.
  - **Uploads** go through Cloudflare's REST API with the same credentials as other scripts (`Services/api/scripts/cloudflare.ts`), retrying its occasional 502s.
- **The viewer** (851-2700): a TanStack Start app in `Web/pixelbook`, deployed as a Worker by the API's stack (`Cloudflare.Website.Vite`) to `pixelbook.lil.tech`, `pixelbook.staging.lil.tech` and each PR preview. Every stage reads the same published snapshots, `main`'s by default (`?ref=` for another branch, `?commit=` with a full SHA for a commit).
  - **Styled with Tailwind CSS** (851-2760): utility classes in the components, through Tailwind's Vite plugin, and Pixelbook's colors and fonts as theme tokens in `src/styles.css`, in light and dark, following the system's appearance (written with `light-dark()`, which Tailwind turns into `prefers-color-scheme`, so a page-level `color-scheme` wouldn't switch them). Body text is 13 px while the root stays at 16, so Tailwind's spacing keeps its sizes.
  - **UI primitives come from [Base UI](https://base-ui.com)** (851-2795, `@base-ui/react`, MIT), wrapped and styled in `src/comps/`, rather than hand-rolled: buttons (Button; a link that looks like one stays an `<a>`), the filters' checkboxes (Checkbox), segmented controls (Toggle Group: the arrow keys move between options), the shortcuts (Dialog: it keeps focus, Escape closes it, and focus goes back to what had it), the layers list's apps and screens (Collapsible, their open state kept by the list) and the hints on buttons (Tooltip, which only sighted users see, so controls keep their `aria-label`s). Base UI handles the semantics, focus and keys; the wrappers restyle it through its state attributes (`data-checked`, `data-pressed`…) with Pixelbook's tokens, and keys show a focus ring in the accent. Feature code uses the wrappers, not Base UI directly.
  - **App shell** (851-2762): a header across the top (Pixelbook, the commit or branch, a comparison's base and Show all, Grid and Flow, the count and zoom), a left sidebar with the filters as lists, the canvas, and the selected snapshot's inspector on the right, side by side rather than floating over the canvas. The sidebar can be dragged between 200 and 400 px (remembered) and hidden from the header. Below 900 px it starts hidden and overlays the canvas when shown, as the inspector does below 1024 px. Fit and the start view use the canvas's own size.
  - **Linear's look** (851-2761): the theme copies Linear's, read from its web app's computed styles in Chrome, in light and dark (values only, nothing from the workspace).
    - **Colors:** its page (`--bg-color`), panels (`--color-bg-primary`), borders (`--color-border-secondary`), three levels of text, a selected and a hovered fill, and its indigo accent (#5e69d1, lighter in dark so links pass AA), as LCH values.
    - **Type:** Inter (`@fontsource-variable/inter`, OFL) at its sizes (12, 13, 15 and 18 px) and its normal weight of 450, preloaded with the page so text doesn't reflow into it. Berkeley Mono is commercial, so monospace stays the system's.
    - **Controls:** 8 px corners, 24 px chips and segments, opaque panels with its soft shadow rather than blurred ones. Chips are a subtle fill when on and dashed when off, rather than solid blue.
  - **Grid mode:** an infinite canvas (drag or scroll to pan, pinch or ⌘-scroll to zoom), with an app per section and a screen per row. Each state's light and dark images sit side by side, in source order, at their size in points. It opens at the top left at a readable zoom; Fit shows everything.
  - **The canvas is React Flow** (851-2766, `@xyflow/react`, MIT, no Pro): tiles, labels and flowchart screens are custom nodes, laid out by Pixelbook as before (`src/lib/Elements.ts`). The flowchart's routes and their labels are one node, sized to reach them all, rather than React Flow edges: it culls an edge by the box of the nodes at its ends, and dagre routes some, such as those back to an earlier screen, around them. React Flow pans, zooms and fits, and is a base for selection, shortcuts and a layers list. It replaced Pixelbook's own canvas, whose input was applied once a frame (851-2714) and which rendered a snapped region around the view (851-2713).
    - **Input:** scrolling pans 1:1 and pinching or ⌘-scrolling zooms, as before; double-clicking doesn't zoom, since it's clicking a tile twice, and Shift-dragging pans, since nothing is selectable. A press that moves 4 points is a drag, not a click. The canvas handles what React Flow doesn't: Safari's trackpad pinch, which arrives as gesture events (on a touch screen React Flow zooms with the touches), and wheels that scroll by pages.
    - **Only what's in view renders** (`onlyRenderVisibleElements`): about 35 of 450 nodes at the start view. Nodes come with their sizes, and no handles, so none render just to be measured, and the server renders none. Culling by 851-2713's region instead, with React Flow's `hidden`, cost more: every node React Flow mounts reads its store on every frame of panning, hidden or not. Off-screen content is out of the DOM, so out of tab order and the browser's find.
    - **Speed,** on production builds, 2 s of synthetic wheel input at 125 events a second (a 120 Hz display's): frame times match the old canvas's (95th percentile 10 ms, none over 20 ms), and script time is about twice its panning (81 ms against 35) and a third more pinching (164 against 123), since React Flow renders its viewport on each event. Its minimap doubled panning's script time, so there's none; the header has the zoom controls.
  - **Selection and shortcuts** (851-2765), as in Figma: the selected frame (the `tile` in the URL, which the inspector shows) has an accent outline, and a hovered one a lighter one, 2 screen pixels at any zoom. Clicking the empty canvas or Escape deselects.
    - **Keys:** the arrow keys move the selection: right and left along a flowchart screen's routes, to the nearest screen at their other ends, and otherwise to the nearest frame that way, scoring distance along plus twice the distance across, so the next in a row wins. The canvas pans to show it. ⇧1 shows everything, ⇧2 zooms to the selection, + and − (with ⌘ too, instead of the browser) zoom, and Space-dragging pans, as React Flow does. `?` lists them, and so does a button in the header. Keys typed into a field aren't shortcuts.
  - **The layers list** (851-2763), in the sidebar under the filters, as Figma's: what's on the canvas by app, screen and state, in the canvas's order, built from the same layout (`src/lib/Layers.ts`). In the grid each tile is a row, its appearance beside its state; in a comparison a change's before and after are one row, with its badge (Changed, New or Removed), choosing the after; on the flowchart a screen's rows are its states. Apps start open and screens closed. Choosing a row steps its flowchart screen to it if need be, selects it and zooms to it, animated. Selecting on the canvas opens its screen in the list and scrolls to it. A search field keeps the screens and states whose names contain it (a matching screen keeps all its states), and Escape clears it.
  - **The inspector** (851-2764), on the canvas's right, as Figma's: the selected frame's details (app, platform, screen, state, appearance, size and scale, and its catalog state's file and line on GitHub at the commit it was published from), and Zoom to, Open image and Copy link. It doesn't show the frame's image again (851-2788): the canvas shows it, and each appearance is its own tile. The flowchart shows one appearance per state, so the details link to the other's image. A comparison's changed frame shows its before and after side by side, overlaid with the after's opacity on a slider, or split by a divider to drag. With nothing selected it sums up what the canvas shows: the commit, the count, the apps and, in a comparison, what changed. That summary shows only in windows at least 1,280 px wide, so a smaller one keeps the canvas's room; a selection shows at any width, over the canvas below 1,024 px.
  - **Filters** for app, platform and appearance, and the selected snapshot, live in the URL, so a view can be shared. A snapshot opens full size with its source file and line, linked on GitHub at the commit it was published from.
  - **Mac snapshots** are transparent, so they're shown over the window background color of their appearance: `#FFFFFF` and `#1E1E1E` on current macOS.
- **Flowchart mode** (851-2701): catalogs don't say how screens connect, so each app has a graph file, `Web/pixelbook/graphs/<app>.json`, drafted by an agent and reviewed.
  - **Format:** `screens` are nodes, each naming its state catalog as `Module/File.swift` (`"screen": "HealthMacApp/SummaryCatalog.swift"`), optionally which `states` to show and in what order, and a `nudge` ([x, y] points) for the automatic layout. `edges` go `from` one screen's `id` `to` another's, with a `label` for the action ("Choose a metric").
  - **With the viewer, not the snapshots:** graphs are bundled into the viewer, so a PR's preview shows that PR's graphs, and editing a graph doesn't change the snapshot key.
  - **The check:** `Web/pixelbook/scripts/graphs.ts` reads each app's state catalogs and their states from the catalogs' manifests (851-2949, 851-2955), and fails if a graph names a catalog, state or screen that doesn't exist in its app, or if a manifest is out of date. It ran on `#Preview("…")` names in LilPackage's sources too, until the last previews became catalogs (851-2969). It runs in the pre-commit hook when catalogs, their manifests or graphs change (`scripts/check --pixelbook`), and as a test. A graph screen with no snapshots published for its app shows as a placeholder node rather than vanishing.
  - **A file with several screens** (a list and its detail, say) is several graph screens, each with its own `title` and `states`. Then every state in that catalog must be on one of them, which the check enforces, so a new state there can't go missing (851-2702). A single screen's `states` is just a selection.
  - **The drafts** (851-2702) cover every screen of lil health on Mac and iPhone, with edges labeled by the action that leads there. On the Mac, a metric's detail is the hub: however a metric is opened (a category, a Summary row, search), its detail is a chart or one of the per-type screens (Sleep, Workouts, ECG…), so those hang off it with "For …" labels. The iPhone's include the Not Now exits and the launches that skip consent or access.
  - **Layout:** dagre, left to right, then nudges. A node shows one state, with ‹ › to step through the rest stacked behind it. It's sized by its first state, so edges meet what's on screen. The flowchart shows one appearance, light unless only dark is on. Screens a graph leaves out sit in rows below, "Not in the graph", so gaps are easy to spot.
- **What changed** (851-2704): `?commit=<head>&base=<base>` compares two commits' snapshots. Images are named by a hash of their bytes, and a reference only changes when it's recorded again, so a snapshot changed exactly when an appearance's image key differs: no pixel threshold. Snapshots are matched by ID (`<screen>.<state>`), so a renamed state is one removed and one new.
  - **The view** is the grid with only what changed: each changed state's differing appearances before and after, side by side and badged (an overlay can come later), and new or removed ones on their own. A snapshot opens with both sides.
  - **On each PR**, `pr.yml`'s `pixelbook` job publishes the PR's head, and comments the count ("2 changed, 1 new on 2 screens since abc1234") with a link to the comparison on pixelbook.lil.tech, updating one comment per push. The base is the PR's merge base with its target, or the nearest commit before it with snapshots (`commits/<sha>.json`, within 20), since main.yml may not have published it yet. A comparison whose base has no snapshots shows the head's, saying so. UI-only PRs get it too, since the job has no paths filter. The PR's preview Worker isn't needed: every Pixelbook reads every commit's snapshots.
  - **The key's inputs** are listed in `scripts/pixelbook`, so changing that list (as 851-2703 and 851-2955 did) gives older commits different keys than they were published under. Publishing any commit again, from git, gives it snapshots under the current list.
- **lil messages** (851-2705, 851-2968): its state catalogs, in `MessagesSnapshotTests` (whose manifests say `messages-mac`), publish as `messages-mac`, with a graph like lil health's.
  - Its sent iMessage bubbles are one solid blue, not Messages.app's gradient across the visible thread. The gradient followed the scroll position, so a snapshot's colors depended on when it was drawn, and dropping it was simpler than chasing every update (our call, after it made a preview flaky).
- **Backgrounds** (851-2708): snapshots are transparent where nothing draws, so the viewer shows them over their platform's background for their appearance: iOS's system background (white or black) for the iPhone's, the window color for the Mac's. Over the canvas, dark mode's white text was nearly invisible.
