# Pixelbook

<!-- Part of docs/DECISIONS.md, the index of decisions (851-2791). -->

An infinite canvas of every app state, from the state catalogs' committed images (851-2955; rendered from SwiftUI previews before), as a grid or a flowchart, with "what changed" on each PR (851-2696).

- **Published from the state catalogs** (851-2955, 2026-10-22): Pixelbook shows the catalogs' committed references, published by CI from git, and no longer renders. Rendering previews was paused on 2026-10-20 (851-2816): the iPhone simulator kept hanging or failing renders (a run once hung silently for 47 minutes), and with several worktrees and agents on one Mac, the render lock (851-2805) queued work for 30+ minutes. Publishing committed files can't hang, needs no Mac, and runs for every PR and merge. The renderer below (Capture, and The fork) stays until 851-2969 removes it with SnapshotPreviews, unused; 851-2814, 851-2767, 851-2769 and 851-2809 go with it.
- **Snapshot tests** (851-2931): swift-snapshot-testing renders Mac preview states in `swift test` (`HealthSnapshotTests`, AGENTS.md), offscreen with `CALayer.render(in:)` at 2x, with no Xcode, Screen Recording or render lock. Six states took 0.1–0.3 s each, and matched pixel for pixel across 16 runs (two of them at once) and between a Retina MacBook and a mini's 1x display over SSH. They match `RenderPreview` except Liquid Glass, which only draws on screen. They're the start of developing without Xcode open; Pixelbook could render its Mac snapshots the same way rather than capturing the screen. iPhone snapshots still need the simulator: they rendered the same way in a hostless test, but `xcodebuild` took 30 s to 9 minutes to start the runner.
  - **A fixed "now", calendar, locale and database** (851-2950), so state catalogs' images only change when the UI does, with no clock hook (SnapshotPreviews' goes with it, 851-2969). `HealthDatabase` has `previewNow` (Tuesday, August 13, 2024, 3 PM in Los Angeles: Pixelbook's day, but the afternoon, since its 07:00 UTC is midnight there and leaves today without data), `previewCalendar` (Gregorian, Los Angeles, `en_US`) and `catalogDatabase`, the preview data built from them once per process. Catalogs pass `previewNow` and `previewCalendar` to whatever asks for the date, and a catalog's suite makes the database, date, calendar, time zone and locale dependencies theirs (`.dependencies { … }`). `fixTimeZoneAndLocale()` (`HealthSnapshotTests`, called first by the suite's trait, which runs before its `init`) makes the calendar's time zone and locale the test process's, with the Mac's format settings (24-hour time, first weekday, units) overridden in the process's argument domain, as `-AppleLocale` does: text a view formats itself (`formatted()`) follows the process's locale, not the environment's, and came out in French under a French one. `Locale.current` is read once, so a test fails if anything read it before. Every state rendered the same with `-AppleLocale de_DE -AppleICUForce24HourTime YES` and with `-AppleLocale fr_FR -AppleMetricUnits YES` on the command line, and "Steps, week" failed without the fix. `makePreviewHealthDatabase()` without arguments takes the `date` and `calendar` dependencies (the wall clock in previews), so a test can show catalogs' rows don't follow them. `#Preview`s keep `.now` until they're deleted.
  - **State catalogs** (851-2949): a screen's states move from `#Preview`s into a catalog in the test target (`StateCatalog`, AppKit-free so the iPhone and lil messages can share it), and its previews are deleted. One parameterized test per catalog snapshots every state in light and dark, at the state's width and at least its height, growing to its content as Pixelbook's snapshots did. A state records its `#fileID` and `#line`, for failures and Pixelbook's source links (851-2955). Graphs name a catalog's file and states as they named previews. References are all committed (Alexandru, 851-2948): Metric Detail's 17 states are 34 images, 3.3 MB, 43–120 KB each (96 KB on average), and its test takes about 10 s on a loaded laptop.
    - **Manifests** (851-2955): a catalog's test also writes its screen's manifest beside its references, `__Snapshots__/<Catalog>/<screen>.json` (`CatalogManifest` in `StateCatalog.swift`): the app (`pixelbookApp`, the test target's), the screen, the catalog as graphs name it (`Module/File.swift`), and each state's name, ID (`<screen>.<state>` slugs), source file and light and dark references, from the repository's root. A catalog can't be read without running it: `SignInCatalog` shares states between the Mac and the iPhone, under a different screen on each, and adds one on the Mac only, behind `#if os`. The test writes the manifest when it's missing or differs, once per screen and process from the whole catalog (so a filtered run writes all of it), and fails unless it's recording, as SnapshotTesting does with a missing reference. A test can't see a manifest it no longer writes, and the iPhone's only run after merging, so the graph check (`manifestProblems` in `graphs.ts`, before every commit that touches catalogs) also fails on a manifest whose catalog file is gone or whose screen isn't in it any more (renamed), a state it has that its file doesn't, a missing reference, and a `CatalogState("…")` in a catalog file that no manifest has. Lines aren't in it, so editing a catalog doesn't make it stale (the iPhone's tests only run after merging): publishing finds each state's `CatalogState("…")` line in its file.
  - **Within 1 per color channel** (851-2985): an image matches its reference when every pixel's channels (alpha included) are at most 1 apart, and fails on any pixel further apart, or a different size (`snapshotChannelTolerance`, `HealthSnapshotTests/MacSnapshot.swift`). References recorded on a laptop on macOS 27.0.1 (26A434) failed on the minis' 27.0 (26A428) exactly that far apart: 851-2952's and 851-2964's 14 failed images had 30 to 6,370 pixels changed (an avatar's `.gray.gradient`, the toolbar search field, SF Symbols), every one by exactly 1, and looked identical. A real change is much further apart: a workout map that changed on the minis the same day had 835,016 pixels changed by up to 222. Moving anything with an edge (text, a symbol, a border) by a pixel, or recoloring by 2 levels or more, fails, which `SnapshotToleranceTests.swift` checks on made-up images. What passes can't be seen: a smooth gradient or soft shadow moved a pixel (its neighbors are 1 apart), a nearly transparent pixel's change, or a color 1 level off. `perceptualPrecision` was the alternative: a color difference (ΔE) per pixel, measured by Core Image. 0.98, the usual choice, allows ΔE 2, which is 4 or 5 levels of gray and more in some hues, so it would pass a slightly retinted background, while a 1-level change is ΔE 0.35–0.45 in grays. A fixed limit on channels is easier to reason about, and the same in every hue. `scripts/snapshot`'s diff marks only pixels beyond the limit, and says by how much they differ and how many more differ within it.
  - **Whole windows** (851-2952): `WindowCatalog` snapshots `AppView` in its states. A snapshot test holds the main queue (a main-actor test runs on it) until the image is taken, so nothing a view starts asynchronously arrives: no `.task` runs, and a `@Fetch`'s first value, which `MainQueueScheduler` delivers on the main queue, never comes. Deterministic, but a category came out blank. So the window's test sets `fetchesFirstValueAtOnce` (a `HealthDatabase` dependency, off in the app), which makes `MainQueueScheduler`s fetch the first value on the spot, and its pages show their data; pages that load in a `.task` (a metric's chart, Sleep's nights) show as loading, as a preview's first frame did. Requests read the date and calendar from dependencies inside `fetch`, which SQLiteData runs with the dependencies of where the fetch started. The sidebar floats in Liquid Glass on macOS 26, so it doesn't draw offscreen, rows, search field and sync footer included (851-2957); the footer has its own catalog.
  - **iPhone catalogs** (851-2953): run in the iPhone 18 Pro simulator, hosted by an empty app (`PhoneSnapshotHost`), and drawn through the window server (`drawHierarchyInKeyWindow`), so Liquid Glass renders (swift-snapshot-testing issues #1029 and #1019); 851-2931's hostless spike drew the glass Settings button nearly invisible. `scripts/snapshot --iphone` runs them.
    - **An Xcode project, not a SwiftPM target:** a package's test targets can't have a host app. `HealthPhoneSnapshotTests` is a test target in `Tools/PhoneSnapshots/PhoneSnapshots.xcodeproj`, which is in `Lil.xcworkspace` so it builds against the package's products and pins with no copy of its own (Pixelbook's project syncs its pins). Its sources stay in `LilPackage/Tests/HealthPhoneSnapshotTests` (a synchronized folder, whose PNGs `EXCLUDED_SOURCE_FILE_NAMES` keeps out of the test bundle: a folder in its membership exceptions didn't), next to the Mac's catalogs, where Pixelbook's graph check finds them, and it builds `StateCatalog.swift` and `SnapshotOutput.swift` from `HealthSnapshotTests`. It depends only on `HealthPhoneApp`, `HealthUpload`, `HealthCatalog`, `LilAuth` and `LilAPI` (for the sign-in catalogs, 851-2967), TCA, swift-dependencies' test support and SnapshotTesting: the Mac's target would pull in Sparkle and `LilCLI`. Its committed scheme sets the host's locale (`en_US`) and time zone.
    - **One simulator, one runtime:** a simulator of the script's own (`lil-snapshots`), on iOS 27.0, which the laptop and the minis both have (the minis also have 27.1), so references match across Macs. Kept booted between runs, booted while the build runs, and checked to answer (`simctl spawn … launchctl list`), since under load a booted simulator can hang every request. Boots get three tries, the last on a new simulator. `xcodebuild` runs the built `.xctestrun` (no package resolution), with a time limit per run (10 minutes since 851-2967, whose 80 more states took 4 minutes at load 60; 5 before) and one retry on a freshly booted simulator, as 851-2814 planned for Pixelbook. One run per Mac at a time (`lockf`).
    - **The same image every run:** each state is shown full screen in the host's key window (its own controller, with the state's style as its traits; the window's own style isn't switched, which left the glass button's rim different in some runs), left 0.5 s to settle, then the window is drawn with `drawHierarchy(in:afterScreenUpdates:)` (what SnapshotTesting's `drawHierarchyInKeyWindow` does) into 8-bit sRGB, as the Mac's are. The window rather than the state's view (851-2967), so an alert it presents is in the image; Pixelbook's iPhone snapshots never showed alerts. An alert takes the window's style, not its presenter's, so a presented controller is given the state's and 0.3 s more to settle. Only the state's own layers lose their animations: removing the alert's too left its glass platter undrawn, its text over the screen. The simulator's default, 16-bit Display P3, made images twice the size, and its in-memory image compared against a decoded reference with color differences of up to 11. Every animation in the state's own layers is removed before drawing, so spinners and indeterminate bars draw at rest: frozen instead (`layer.speed = 0`), a spinner came out at a different step in each run.
    - **Within 2 per color channel**, where the Mac's are within 1 (851-2985): even so, the glass Settings button's rim came out 1 or 2 apart in a channel, in about one image in ten (68–141 pixels, nothing else changed): the window server's rounding, not the view (`phoneChannelTolerance`, `PhoneSnapshot.swift`). The shared parts, the images `scripts/snapshot` gets, their diffs and the channel tolerance, are in `HealthSnapshotTests/SnapshotOutput.swift`, which both targets build. SnapshotTesting's perceptual tolerance (`perceptualPrecision: 0.97`) passed too, but per channel is the Mac's rule, and stricter.
    - **The status bar** is the system's, so it isn't in the images; the safe area is.
    - **The screen's height** (851-2967): a state fills the screen, as the app shows it, where Pixelbook grew an iPhone preview to its scroll content. What scrolls below (the rest of Settings, a long log) isn't in the image, and no scroll edge effect needs hiding (851-2716), since nothing is expanded. Drawing through the window server can't draw past the screen.
    - **Torn down within the test** (851-2967): SwiftUI can update a view after its test has ended, outside the test's dependencies, where reading the date reported an issue in no test (`ConnectedAgentRow`'s "Last used"). Each state's controller is dismissed and removed, and the run loop turned once, before the test ends, and the iPhone's Connected Agents reads the date where the catalog makes it and passes it to its rows.
    - **Shared with the Mac** (851-2967): the sign-in screens, which both apps show, have one catalog each in `HealthSnapshotTests/Catalogs/LilAuth`, which the iPhone's target builds by reference, so Pixelbook's graphs name one file for both apps. Each target renders it as its app does (`#if os(macOS)`), with the platform in the screen's name (`Sign In (Mac)`, `Sign In (iPhone)`), since both platforms' references share its `__Snapshots__` folder. A Mac-only state is added under `#if os(macOS)`. The iPhone's branch is `#elseif PHONE_SNAPSHOT_TESTS`, a condition only that target sets, so the package's test target still builds for iOS. Each such file is a file reference in the iPhone's project (its synchronized folder is `HealthPhoneSnapshotTests` only), and the folder's `__Snapshots__` an `exclude` in `Package.swift`.
    - **CI:** after every merge to `main` that touches Swift, on a mini (`iphone-snapshots` in `swift-check.yml`), in a simulator of the job's own that it deletes. Not for pull requests (851-2948's decision 4): a cold simulator and runner take minutes, and a busy mini can take much longer. A failure uploads the images and diffs.
- **Capture:** [SnapshotPreviews](https://github.com/getsentry/SnapshotPreviews) (MIT), through our fork [851-labs/SnapshotPreviews](https://github.com/851-labs/SnapshotPreviews) (branch `lil`, pinned to a tag such as `0.20.0-lil.9`), finds every `#Preview` in a test binary and writes a PNG and a JSON sidecar (module, file, preview name, line) for each. `scripts/pixelbook render` runs it for each app, light and dark.
  - **Side by side** (851-2749): the Mac's runs and the iPhone's go at the same time, since the iPhone's run in the simulator, apart from the screen the Mac's windows are captured on. Within each, runs go one after another: two Mac test runs at once hang (each stopped after two previews), and the iPhone's appearance is the simulator's. On a warm build (about a minute), rendering 450 images took 115 s, the Mac's runs, against about 160 s one after another. The Mac's runs are the critical path: about a second of each chart preview's goes to querying the synthetic database it reads.
  - **One render at a time, and a runner that never starts is tried again** (851-2805): renders in two worktrees shared the simulator, so one installing its test host killed the other's runs (twice in a day). A render now runs holding a lock for the Mac (`lockf` on `/tmp/pixelbook-render-<uid>.lock`, which the kernel lets go of when the render ends), so another waits, building included, for 30 minutes at most. Separately, the simulator's test runner twice never connected ("timed out while preparing to run tests", "hung before establishing connection") with a second simulator booted, rendering nothing. Such an iPhone run is tried again in a restarted simulator, twice at most, keeping each failed try's log; a test host that crashes at launch isn't retried.
  - **Its own project,** `Tools/PixelbookSnapshots/PixelbookSnapshots.xcodeproj`, so LilPackage's tests and the pre-commit hook don't render previews. It has a test target per app.
  - **Pins:** the project's pins are copied from LilPackage's `Package.resolved` before each run, so previews render against the apps' library versions.
  - **Mac previews** render in a plain test target. The app's appearance is set from `PIXELBOOK_APPEARANCE`.
  - **iPhone previews** need a running app, so their test is hosted by an empty app (`PixelbookHost`) in the iPhone 18 Pro simulator (`PIXELBOOK_SIMULATOR`). The appearance is set by `simctl` and put back afterwards.
  - **Preview dependencies:** everything renders with `SWIFT_DEPENDENCIES_CONTEXT=preview`, as in Xcode. Not with `XCODE_RUNNING_FOR_PREVIEWS`, which switches SwiftUI into its preview layout and changes image sizes.
  - **Warnings:** a preview that reports an issue (a runtime warning in Xcode) fails its test but still renders, so `render` warns and `check` fails. A run that renders nothing fails `render`.
  - **Determinism** (851-2698): snapshots must only change when the UI does, so `scripts/pixelbook check` renders twice and fails if any image's pixels differ, or if a preview reports an issue.
    - **The clock:** SnapshotPreviews fixes it, hooking `gettimeofday` at August 13, 2024, 07:00 UTC (on arm64), so previews that use the current date render the same every day. The script fixes the time zone (`TZ`), so day boundaries don't move with the machine or daylight saving time. The locale is still the machine's.
    - **The database:** previews whose views read it called `preparePreviewDatabase()` (`HealthDatabase`) first, rather than reading a blank one (and, in Pixelbook, whatever an earlier preview prepared). A preview context kept the first preparation in a process, so every preview shared one synthetic database, built once, which previews only read. Snapshot catalogs replaced it: their suite makes `catalogDatabase` the `defaultDatabase`, and the function went with Health Details' previews, the last that called it (851-2965).
    - **Alerts:** previews that show an alert give their `EmptyReducer` an `ifLet`, so closing it (when a snapshot's window goes) clears it, as the feature does.
    - **The system's appearance:** Pixelbook sets each run's appearance on the app (`NSApplication.shared.appearance`), but drawing outside any view, such as an `NSImage` drawing handler rendered for its data, takes the current drawing appearance, which followed the system's. On a Mac that switches between light and dark automatically, lil messages' synthetic contact photo changed at sunset (851-2751). Such drawing names its appearance (`NSAppearance(named: .aqua)?.performAsCurrentDrawingAppearance`), and draws into a bitmap of a fixed pixel size rather than the screen's scale. `check` can't catch it, since both of its runs share the system's appearance.
  - **Broken framework signature:** SnapshotPreviews ships `PreviewsSupport.framework`'s macOS slice with a broken signature, which macOS refuses to load and may move to the Trash as malware ([issue 236](https://github.com/getsentry/SnapshotPreviews/issues/236)): it seals Swift module files the framework doesn't ship. Our fork signs it ad hoc (851-2748, `0.20.0-lil.9`), and must again after merging upstream's framework; it's only a test dependency and never ships. The script checks the signature after resolving packages, and if a fork update brings the broken one back it stops with what to do, blocking a push as a preview's issue does. The other slices (the iPhone simulator's among them) have the same broken signature, which the simulator doesn't enforce, so they're left as they are.
  - **Scroll expansion** (851-2706): SnapshotPreviews grows a preview until its first scroll view shows all its content. A preview held to a fixed height (`.frame(width:height:)`) doesn't grow, so it came out centered in a taller snapshot, or shifted down and cut off: a blank band above the content. Mac previews size themselves with `previewFrame(width:height:)` (`HealthUI`) instead. In Pixelbook (`PIXELBOOK=1`, set by the script) the height is only a minimum, top-aligned, so previews grow and the snapshot shows everything, as the iPhone's do. In Xcode's canvas it stays fixed: a scroll view free to size to its content made the canvas time out. Turning expansion off (`.snapshotExpansion(false)`) would make the apps depend on SnapshotPreviews. Our fork grows it to the content's height rounded up to the screen's pixels, done within half a pixel (851-2768, `0.20.0-lil.11`): upstream grew by the difference truncated to whole points each pass, so a list that settled over a different number of passes came out a pixel or two shorter in some runs. Rounding to pixels, rather than keeping fractions of a point, can't swing between two heights as layout snaps frames to pixels.
  - **Some previews:** `PIXELBOOK_PREVIEWS` renders only the previews matching its comma-separated regular expressions, matched against `Module/File.swift:Name`, for trying a change quickly (`check` takes it too). A filter that matches nothing fails. `publish` ignores it.
  - **Diagnostics:** `xcodebuild` runs with `-collect-test-diagnostics never`, since collecting simulator diagnostics after a run could hang it for many minutes. Plain `swift test` couldn't load the binary framework, so it's `xcodebuild` throughout.
- **Publishing** (851-2699, 851-2955): `scripts/pixelbook publish [--commit <sha>] [--ref <name>]` uploads a commit's state catalog images to the R2 bucket `lil-pixelbook`, public at `pixelbook-assets.lil.tech` (read-only, CORS open), which every stage's Pixelbook reads. Only prod's stack creates it, since there's one set of snapshots.
  - **From git, not a render:** the uploader (`Services/api/scripts/pixelbook.ts`) lists the commit's `LilPackage/Tests` (`git ls-tree`), reads every catalog manifest, its states' sources and its references as blobs, and builds each app's manifest from them. So any fetched commit can be published, with no Xcode, simulator, Screen Recording or lock, on Linux, and the working tree doesn't count. A manifest whose catalog file is gone, or a state without a reference, is left out with a warning (`::warning::` on GitHub). Only catalogs are published: screens still on `#Preview`s aren't in Pixelbook until they're migrated (lil messages, 851-2968), and show as placeholders in the flowchart.
  - **Keyed by inputs, not commits:** a key is a hash of the git trees snapshots come from: every test target's `Catalogs` folder (sources, references and manifests), `scripts/pixelbook` and the uploader. A squash merge makes a new commit, but its trees match the branch's, so main finds the branch's snapshots, and a commit that changes no catalog shares its parent's.
  - **Layout:** `images/<sha256 of the PNG>.png`, each stored once, so an unchanged screen isn't uploaded again. A reference's bytes only change when it's recorded again, so they're hashed rather than its pixels (renders' PNG metadata differed run to run; references are committed). `snapshots/<key>/<app>.json` is an app's manifest (screen, state, catalog module and file, the state's source path, line and place in its catalog, and each appearance's image, size and scale), and `snapshots/<key>/index.json`, written last, marks a key complete. `commits/<sha>.json` and `refs/<branch>.json` point at keys.
  - **Snapshot IDs** are `<screen>.<state>` slugs, which name the references, so renaming a screen or state is one removed and one new, and moving a catalog changes nothing. A comparison across the switch from previews shows every screen removed and new, once.
  - **Source links** use the state's file (`path`) and line: its `CatalogState("…")`, found by name in the file at that commit, as `#line` gives it. Previews' manifests (851-2790) had the preview's file, found under `LilPackage/Sources/<module>`.
  - **States in their catalog's order** (`order`), not their lines', since shared states can be written after a platform's own.
  - **Thumbnails** (851-2712): `thumbnails/<the same sha256>.png` is each image at a quarter of its width and height, and the manifest names it. Zoomed out, the canvas would otherwise load and decode every snapshot at full size (about 100 MB at Fit), so tiles use thumbnails while they'd hold at most half a screen pixel per point, which a quarter-size Mac (2x) image still has; the detail panel always shows the original. Made in Node (`Services/api/scripts/png.ts`: zlib, a box filter weighted by alpha, Paeth rows), since CI's Linux has no `sips`: about 90 ms an image, 22 KB on average. PNG, for transparency.
  - **Skipping work:** a published key is only pointed at: `publish` writes the commit's and ref's pointers, and only those that changed. A second run uploads nothing.
    - A branch's pointer doesn't move back to an older commit (a re-run of an earlier merge's job), unless `--force-ref` (a PR's push, which is the branch even when it rewinds).
  - **When:** in CI, which has the deploy token: `pr.yml`'s `pixelbook` job publishes each PR's head (and points the branch at it), and `main.yml`'s publishes each merge and points main at it, in order. A PR doesn't publish its base: it would be published with the PR's copy of the uploader under a key made from the base's, and a key with an index is never published again, so a PR changing the uploader could fill main's keys with its own output. Each commit is published by its own scripts, which are in its key. Nothing runs before a push any more; lefthook's pre-push hook (851-2703) rendered and published there, on the developer's Mac, until it was paused. Publish by hand with `scripts/pixelbook publish`, which needs a Cloudflare login.
  - **Uploads** go through Cloudflare's REST API with the same credentials as other scripts (`Services/api/scripts/cloudflare.ts`), retrying its occasional 502s.
- **The viewer** (851-2700): a TanStack Start app in `Web/pixelbook`, deployed as a Worker by the API's stack (`Cloudflare.Website.Vite`) to `pixelbook.lil.tech`, `pixelbook.staging.lil.tech` and each PR preview. Every stage reads the same published snapshots, `main`'s by default (`?ref=` for another branch, `?commit=` with a full SHA for a commit).
  - **Styled with Tailwind CSS** (851-2760): utility classes in the components, through Tailwind's Vite plugin, and Pixelbook's colors and fonts as theme tokens in `src/styles.css`, in light and dark, following the system's appearance (written with `light-dark()`, which Tailwind turns into `prefers-color-scheme`, so a page-level `color-scheme` wouldn't switch them). Body text is 13 px while the root stays at 16, so Tailwind's spacing keeps its sizes.
  - **UI primitives come from [Base UI](https://base-ui.com)** (851-2795, `@base-ui/react`, MIT), wrapped and styled in `src/comps/`, rather than hand-rolled: buttons (Button; a link that looks like one stays an `<a>`), the filters' checkboxes (Checkbox), segmented controls (Toggle Group: the arrow keys move between options), the shortcuts (Dialog: it keeps focus, Escape closes it, and focus goes back to what had it), the layers list's apps and screens (Collapsible, their open state kept by the list) and the hints on buttons (Tooltip, which only sighted users see, so controls keep their `aria-label`s). Base UI handles the semantics, focus and keys; the wrappers restyle it through its state attributes (`data-checked`, `data-pressed`…) with Pixelbook's tokens, and keys show a focus ring in the accent. Feature code uses the wrappers, not Base UI directly.
  - **App shell** (851-2762): a header across the top (Pixelbook, the commit or branch, a comparison's base and Show all, Grid and Flow, the count and zoom), a left sidebar with the filters as lists, the canvas, and the selected snapshot's inspector on the right, side by side rather than floating over the canvas. The sidebar can be dragged between 200 and 400 px (remembered) and hidden from the header. Below 900 px it starts hidden and overlays the canvas when shown, as the inspector does below 1024 px. Fit and the start view use the canvas's own size.
  - **Linear's look** (851-2761): the theme copies Linear's, read from its web app's computed styles in Chrome, in light and dark (values only, nothing from the workspace).
    - **Colors:** its page (`--bg-color`), panels (`--color-bg-primary`), borders (`--color-border-secondary`), three levels of text, a selected and a hovered fill, and its indigo accent (#5e69d1, lighter in dark so links pass AA), as LCH values.
    - **Type:** Inter (`@fontsource-variable/inter`, OFL) at its sizes (12, 13, 15 and 18 px) and its normal weight of 450, preloaded with the page so text doesn't reflow into it. Berkeley Mono is commercial, so monospace stays the system's.
    - **Controls:** 8 px corners, 24 px chips and segments, opaque panels with its soft shadow rather than blurred ones. Chips are a subtle fill when on and dashed when off, rather than solid blue.
  - **Grid mode:** an infinite canvas (drag or scroll to pan, pinch or ⌘-scroll to zoom), with an app per section and a screen per row. Each state's light and dark images sit side by side, in source order, at their size in points. It opens at the top left at a readable zoom; Fit shows everything.
  - **The canvas is React Flow** (851-2766, `@xyflow/react`, MIT, no Pro): tiles, labels and flowchart screens are custom nodes, laid out by Pixelbook as before (`src/lib/Elements.ts`). The flowchart's routes and their labels are one node, sized to reach them all, rather than React Flow edges: it culls an edge by the box of the nodes at its ends, and dagre routes some, such as those back to an earlier screen, around them. React Flow pans, zooms and fits, and is a base for selection, shortcuts and a layers list. It replaced Pixelbook's own canvas, whose input was applied once a frame (851-2714) and which rendered a snapped region around the view (851-2713).
    - **Input:** scrolling pans 1:1 and pinching or ⌘-scrolling zooms, as before; double-clicking doesn't zoom, since it's clicking a tile twice, and Shift-dragging pans, since nothing is selectable. A press that moves 4 points is a drag, not a click. The canvas handles what React Flow doesn't: Safari's trackpad pinch, which arrives as gesture events (on a touch screen React Flow zooms with the touches), and wheels that scroll by pages.
    - **Only what's in view renders** (`onlyRenderVisibleElements`): about 35 of 450 nodes at the start view. Nodes come with their sizes, and no handles, so none render just to be measured, and the server renders none. Culling by 851-2713's region instead, with React Flow's `hidden`, cost more: every node React Flow mounts reads its store on every frame of panning, hidden or not. Off-screen content is out of the DOM, so out of tab order and the browser's find.
    - **Speed,** on production builds, 2 s of synthetic wheel input at 125 events a second (a 120 Hz display's): frame times match the old canvas's (95th percentile 10 ms, none over 20 ms), and script time is about twice its panning (81 ms against 35) and a third more pinching (164 against 123), since React Flow renders its viewport on each event. Its minimap doubled panning's script time, so there's none; the header has the zoom controls.
  - **Selection and shortcuts** (851-2765), as in Figma: the selected frame (the `tile` in the URL, which the inspector shows) has an accent outline, and a hovered one a lighter one, 2 screen pixels at any zoom. Clicking the empty canvas or Escape deselects.
    - **Keys:** the arrow keys move the selection: right and left along a flowchart screen's routes, to the nearest screen at their other ends, and otherwise to the nearest frame that way, scoring distance along plus twice the distance across, so the next in a row wins. The canvas pans to show it. ⇧1 shows everything, ⇧2 zooms to the selection, + and − (with ⌘ too, instead of the browser) zoom, and Space-dragging pans, as React Flow does. `?` lists them, and so does a button in the header. Keys typed into a field aren't shortcuts.
  - **The layers list** (851-2763), in the sidebar under the filters, as Figma's: what's on the canvas by app, screen and state, in the canvas's order, built from the same layout (`src/lib/Layers.ts`). In the grid each tile is a row, its appearance beside its state; in a comparison a change's before and after are one row, with its badge (Changed, New or Removed), choosing the after; on the flowchart a screen's rows are its states. Apps start open and screens closed. Choosing a row steps its flowchart screen to it if need be, selects it and zooms to it, animated. Selecting on the canvas opens its screen in the list and scrolls to it. That summary shows only in windows at least 1,280 px wide, so a smaller one keeps the canvas's room; a selection shows at any width, over the canvas below 1,024 px.

- **Flowchart mode** (851-2701): previews don't say how screens connect, so each app has a graph file, `Web/pixelbook/graphs/<app>.json`, drafted by an agent and reviewed.
  - **Format:** `screens` are nodes, each naming the file its previews are in (`"screen": "HealthMacApp/SummaryViewPreviews.swift"`), optionally which `states` (preview names) to show and in what order, and a `nudge` ([x, y] points) for the automatic layout. `edges` go `from` one screen's `id` `to` another's, with a `label` for the action ("Choose a metric").
  - **With the viewer, not the snapshots:** graphs are bundled into the viewer, so a PR's preview shows that PR's graphs, and editing a graph doesn't change the snapshot key or need a render.
  - **The check:** `Web/pixelbook/scripts/graphs.ts` reads `#Preview("…")` names from LilPackage's Swift sources, and state catalogs' states by app from their manifests (named `Module/File.swift` too, 851-2949, 851-2955), and fails if a graph names a file, state or screen that doesn't exist in its app. It skips commented-out previews; unnamed ones count, though a graph can't name them. It runs in the pre-commit hook when Swift sources, catalogs or their manifests, or graphs change (`scripts/check --pixelbook`), and as a test. It can't tell which modules an app renders previews from, so a graph screen with no snapshots for its app shows as a placeholder node rather than vanishing.
  - **A file with several screens** (a list and its detail, say) is several graph screens, each with its own `title` and `states`. Then every preview in that file must be on one of them, which the check enforces, so a new preview there can't go missing (851-2702). A single screen's `states` is just a selection.
  - **The drafts** (851-2702) cover every preview file of lil health on Mac and iPhone, with edges labeled by the action that leads there. On the Mac, a metric's detail is the hub: however a metric is opened (a category, a Summary card, search), its detail is a chart or one of the per-type screens (Sleep, Workouts, ECG…), so those hang off it with "For …" labels. The iPhone's include the Not Now exits and the launches that skip consent or access.
  - **Layout:** dagre, left to right, then nudges. A node shows one state, with ‹ › to step through the rest stacked behind it. It's sized by its first state, so edges meet what's on screen. The flowchart shows one appearance, light unless only dark is on. Screens a graph leaves out sit in rows below, "Not in the graph", so gaps are easy to spot.
- **What changed** (851-2704): `?commit=<head>&base=<base>` compares two commits' snapshots. Images are named by a hash of their pixels and renders are deterministic, so a snapshot changed exactly when an appearance's image key differs: no pixel threshold. Snapshots are matched by ID (module, file, preview name), so a renamed preview is one removed and one new.
  - **The view** is the grid with only what changed: each changed state's differing appearances before and after, side by side and badged (an overlay can come later), and new or removed ones on their own. A snapshot opens with both sides.
  - **On each PR**, `pr.yml`'s `pixelbook` job publishes the PR's head, and comments the count ("2 changed, 1 new on 2 screens since abc1234") with a link to the comparison on pixelbook.lil.tech, updating one comment per push. The base is the PR's merge base with its target, or the nearest commit before it with snapshots (`commits/<sha>.json`, within 20), since main.yml may not have published it yet. A comparison whose base has no snapshots shows the head's, saying so. UI-only PRs get it too, since the job has no paths filter. The PR's preview Worker isn't needed: every Pixelbook reads every commit's snapshots.
  - **The key's inputs** are listed in `scripts/pixelbook`, so changing that list (as 851-2703 and 851-2955 did) gives older commits different keys than they were published under. Publishing any commit again, from git, gives it snapshots under the current list.

- **The fork** (851-2711): forked rather than depending on SnapshotPreviews in the apps, since it's small (about 2,800 lines that matter) and its settings otherwise live in app code.
  - **Window-filling Mac previews are captured from a real window.** SnapshotPreviews draws views in-process (`cacheDisplay`), which misses what the window server composites: a sidebar's vibrant icons and text, and the title bar and toolbar, which a borderless window doesn't have. A preview that puts something in its window's chrome (a split view, a navigation title or toolbar items, detected after a first render) renders again in a titled window and is captured with ScreenCaptureKit, as the screen shows it, without its shadow. Other previews render as before.
    - The window sits off screen but for a one-point column at the display's right edge, from before it's laid out until it's captured: ScreenCaptureKit refuses windows entirely off screen, but captures partly visible ones at their full size, taller than the screen included. It grows right, and up or down, away from the screen, so it never shows over the desktop.
    - **Held still for capture:** the window server keeps animating what the app no longer draws, so before a capture, spinners stop on their first frame, Core Animation is paused, and overlay scrollers (which flash, then fade) are hidden. It's then captured until two captures in a row match; one that never settles keeps its last capture, which `check` would flag. Captures are then identical run to run.
    - **Never entirely off screen** (851-2750): laid out far off screen, a window's capture was sometimes its surface from before the last resize, stretched to the new size, resampling every edge. ScreenCaptureKit reports the new frame at once, so waiting for it didn't help, and two identical captures could both be stale.
    - **A stream that fails to start is tried again** (851-2769, `0.20.0-lil.13`): ScreenCaptureKit sometimes refused to start a capture (`SCStreamError.failedToStart`, -3811) for a window right after capturing others, though the same window captured on its own; the app window's Health Details preview failed this way 4 times out of 4 in a batch. The cause isn't known. The fork tries again, at most 5 times per capture, 200 ms longer apart each time, looking the window up afresh each time rather than reusing the filter, and logs each retry, which `render` counts. Since then the preview has rendered in full checks, but render order changed too, so it isn't known whether the retries were needed. If a capture still fails, `render` treats it as the machine's doing, as before.
    - **Inactive windows:** the test runner isn't the active app, so windows are captured inactive (grey traffic lights and selection), as a window behind another app's looks. Activating it would take focus from whoever is at the Mac on every capture.
    - **Cost:** a window-filling preview renders twice, borderless to find out that it fills a window, then titled.
    - **Screen Recording:** the test runner is Xcode's, so Xcode needs Screen Recording access once per Mac. Without it, `render` says how to grant it and exits 1, at the first Mac run that hits it, stopping the iPhone's beside it, which the pre-push hook skips on. So does a capture that fails otherwise (a locked screen), since that's the machine's doing, not the previews'. Window capture with `CGWindowListCreateImage` was tried first: it's deprecated, and only gets a window's on-screen part.
  - **Previews are made again as they render,** so each one's traits apply to it, as in Xcode. swift-dependencies' `.dependencies` trait prepares dependencies when a preview is made; made once up front, every preview got the last one's (lil messages' window previews rendered with an empty database).
  - **A preview that fails to render fails its test,** instead of being left out unnoticed.
  - **No scroll edge effects on iPhone** (851-2716): iOS 26's scroll edge effect blurs what's behind a scroll view's top and bottom edges. In previews expanded past the screen's height (the consent screen's), the snapshot drew it as opaque black rows at the top (260–338 pixels), smeared with the content beneath. Screen-sized previews didn't show it. iOS previews render with `scrollEdgeEffectHidden()`; at rest, with nothing scrolled under an edge, the effect shows nothing anyway. It reaches SwiftUI scroll views only (a `UIScrollView` keeps its effect), and a preview can't opt out, which none needs yet.
