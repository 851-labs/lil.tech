# lil health

<!-- Part of docs/DECISIONS.md, the index of decisions (851-2791). -->

- **What it is:** Apple Health on the Mac. macOS has no Health app (as of macOS 27).
  - The iOS app reads Apple Health and uploads it to `api.lil.tech`.
  - The macOS app syncs it and renders it like iPad Health.
- **Why a server:** App Store guideline 5.1.3 forbids storing personal health data in iCloud, so the iPhone can't hand data to the Mac through CloudKit.
- **iOS app:** a minimal bridge: sign in, consent, grant Health access, sync status.
- **Data:** v1 syncs every readable HealthKit type, including workouts and routes, ECG, heartbeat series, audiograms, medications and State of Mind.
  - Clinical records (Health Records) are out of scope, because they need an entitlement that depends on App Review approval. Health Documents (CDA) are a different type, which the standard HealthKit entitlement reads, so they sync (below).
  - Workouts are `health_workout` records: the overall activity type, times and duration, plus their activities (multisport legs), events (pauses, laps, segments) and per-type statistics as JSON, in the catalog's units. The iPhone reads them through the same anchored backfill as samples. Routes come separately (851-2566).
  - State of Mind logs (`health_state_of_mind`) and GAD-7/PHQ-9 assessments (`health_scored_assessment`) keep HealthKit's raw values for kinds, labels, associations, risks and answers, so the Mac can name them in the user's language.
  - Audiograms (`health_audiogram`) keep each tested frequency with its per-ear tests (sensitivity and clamping range in dBHL, conduction type, masking), as HealthKit's iOS 18.1 model has them.
  - ECGs (`health_electrocardiogram`) keep their classification, symptoms status, average heart rate and sampling frequency in the row. The voltages (lead I) are a blob of little-endian 32-bit floats in microvolts, one per measurement, about 60 KB for a 30-second recording. The iPhone reads them 50 ECGs to a page, so a page's blobs stay small in memory. The symptoms themselves are category samples, synced like any other.
  - Workout routes (`health_workout_route`) keep their locations in a blob, 44 bytes each (time, latitude and longitude as 64-bit floats; altitude, accuracies, speed and course as 32-bit), about 160 KB for an hour at 1 Hz. The iPhone reads them 10 to a page. HealthKit only queries routes by workout, so the iPhone finds each route's workout among the workouts its time overlaps and stores it (`workout`, or `null` if none links it). A later blob format would add a `locationsFormat` field; rows without one are this format. They're precise location data, which the privacy policy says.
  - Heartbeat series (`health_heartbeat_series`) keep each beat's time (seconds since the start) and the indices of beats preceded by a gap, as JSON in the row. They're about a minute and a hundred beats each (~2 KB), so a blob per reading would cost an R2 object, a quota row and a download, thousands of times a year, for little. The iPhone reads them 200 to a page, since each needs its own query.
  - Vision prescriptions (`health_vision_prescription`, 851-2572) keep the kind (glasses or contacts), when issued (as start and end) and expiring, a contacts brand, and each eye's lens as JSON: sphere, cylinder, axis and add power, plus glasses' vertex and pupillary distances and prism, or contacts' base curve and diameter, in diopters, degrees and millimeters. Health shares them one by one (per-object authorization), and may share an old one or stop sharing one at any time, which anchored queries don't see, so they're read whole every run, as characteristics are: they go up when they change, and one no longer shared is deleted. Scanned images (`HKAttachment`) aren't uploaded.
  - Medications (`health_medication`, 851-2571) keep the name Health shows, a nickname, the general form (`HKMedicationGeneralForm`'s raw string, any value), whether they're archived or scheduled, and their clinical codings as JSON. Their dose events (`health_medication_dose`) keep the medication, the log status and schedule type (HealthKit's raw values, any integer, so a status a later iOS adds isn't refused forever), the scheduled date and dose, the dose taken and its unit, with the usual times and provenance.
    - **Keyed by concept:** doses only name their medication's `HKHealthConceptIdentifier`, which has no public value but its domain. Its ID is the SHA-256 of the strings it archives (its domain and underlying identifier, collected through `NSKeyedArchiver`'s delegate, all public API), so the same concept gets the same ID on every run and iPhone. If a later iOS archived it differently, IDs would change once, which the sharing rules below absorb: the old medications and their doses are deleted, and the doses read again under the new IDs. Health keeps one medication per concept; if it ever had two, a current one wins over an archived one.
    - **Sharing:** Health shares medications one by one (per-object authorization), with their doses, and may share an old one or stop sharing one at any time. Medications aren't samples, so they're read whole at the start of every run of everything, before the types, and go up when they change (`uploadWhole`, as prescriptions do). Doses are samples, read through the anchored backfill like any type, so the thousands a person logs aren't sent again every run, and deletions come through the anchor. Two things an anchor doesn't see are handled with the medications:
      - A medication shared since may have doses from before the dose type's anchor. When the set of medications grows, the dose type's anchor is forgotten (and its count), so the same run reads every dose again; the server drops the unchanged ones. Only sharing more does this.
      - A medication no longer shared can't have its doses read, so their deletions never come. The iPhone keeps which doses it uploaded for each medication, in a backfill file (`medication-doses.json`) rather than the state, which is saved after every step. A page's doses are noted before it goes up (a page that fails is read again, and deleting a dose the server doesn't have does nothing), and deletions take them out. A medication no longer shared is deleted with all its doses, in one upload, before the state forgets it.
    - Upload Everything Again reads the doses from the start and keeps the medications' hash and IDs and the doses file, as it keeps prescriptions'. Signing out removes the file.
    - On the Mac, Browse dates both medication types by the latest dose. Medications counts as having data once one is shared, even without doses (an as-needed one never logged), undated.
    - **On the Mac** (851-2589): both Browse types open Medications: current ones, then archived ones, by the name they show (the nickname, else Health's), with the form and Scheduled or As Needed. A medication's page shows its adherence over the last 7 and 30 days (today and the days before, in the Mac's calendar): scheduled doses taken out of those scheduled, plus doses taken as needed. Each scheduled dose (medication and scheduled time) counts once, as its latest-logged event, should Health keep several. Below is the log, newest first, by the day a dose was due (when it was logged, for one taken as needed), each with its status (Taken, Skipped, Snoozed, Not Logged…), times and quantity, up to the latest 1,000 doses. There were no iPad reference screenshots to compare with.
  - Health Documents (`health_document`, 851-2836) are clinical documents in HL7's Clinical Document Architecture (CDA), such as a visit summary a provider sent, which Health lists with health records. Each keeps the title, patient, author and custodian names HealthKit extracts (possibly empty), with the usual times and provenance, and its XML as a blob, as Health keeps it (not compressed): they can be large, and the Mac's viewer (851-2837) shows them as they are.
    - **Sharing:** the document type is in the standard sheet, and then HealthKit asks about each document, the first time the app's document query (`HKDocumentQuery`) finds it, in a sheet of its own. Anchored queries list documents without their XML, and don't see one stop being shared, so documents are read whole every run of everything, like vision prescriptions (`HealthDocumentsReader`): which ones are shared (without their XML), then only those not uploaded yet with their XML, 10 to a page, each page's blobs before its rows. Documents never change, so the backfill keeps the IDs it uploaded (`documentIDs`) rather than a hash, and deletes one no longer shared. One too large for a blob (16 MB) is skipped and reported, and kept among the IDs so it isn't read again every run.
    - Nothing asks for documents but the run itself: the first run after Health access may show Health's sheet for them, and so may a later one that finds a new document. Whether a background run can show it isn't known, so documents are read last, after the Activity summaries, in case the query waits on it; if it fails, it's tried again on the next run.
    - **Consent** (decided with Alexandru, 2026-10-20): documents carry names, addresses and diagnoses, but the consent version stays `2026-10-15`. The consent already covers the Health data the person lets lil health read, and documents only sync when the person shares each one in Health's own sheet. The privacy policy lists them.
    - **On the Mac:** `healthDocuments`, synced like any entity. Health Documents opens a list, newest first, and each document a viewer (851-2837): the patient, author, custodian and date HealthKit extracted, then each section of the structured body (its `<title>` and narrative `<text>`) as a card, with paragraphs, lists and tables. The XML downloads when a document opens, through the blob cache, as ECG voltages do. `ClinicalDocument` (`HealthDatabase`) reads it with Foundation's `XMLParser`, in the CDA namespace only; coded entries and images aren't shown. In C-CDA nearly every section's entries repeat its narrative, so only a section with entries but no narrative, or an image (`renderMultiMedia`, `observationMedia`), makes the page say some of the document isn't shown. Narrative elements it doesn't know show their text; superscripts and subscripts stay raised and lowered (10⁹, not 109), and spanning table cells keep later cells in their columns. The XML is decoded in its own encoding (byte order mark, then the declaration), and only as text when it's shown. A document no longer shared says so. Malformed XML, or a document without readable sections (an unstructured `nonXMLBody`, a PDF say), shows its XML instead, saying why; Show XML opens it for any document, in a text view rather than SwiftUI's `Text`, since documents can be megabytes.
  - **On the Mac** (851-2592): Health Details, below Summary in the sidebar, shows the characteristics (date of birth with age, sex, blood type, Fitzpatrick skin type, wheelchair use; "Not Set" when unset) and links to Vision Prescriptions, which the Other Data type opens too: a list, newest first, with expiry, and each prescription's Right (OD) and Left (OS) values, leaving out rows neither eye has.
  - Characteristics (date of birth, sex, blood type…) and Activity summaries have no anchors, so every run of everything reads them. Characteristics go up when their content changes (a hash in the backfill's state). Activity summaries go up all at once the first time, then the last 30 days', whose numbers and goals can still change (e.g. when a Watch that was away syncs). A characteristic that stops being readable is deleted. A locked phone pauses the run rather than looking like removed characteristics.
  - **Upload Everything Again** (851-2662), in the iPhone's Settings sheet with consent: each type's anchor says everything before it is on the server, so history Health starts sharing later (iOS 27's "Past 30 Days and Future Data", widened to All Recorded Data in Settings) would never go up. After a confirmation, `HealthBackfill.uploadAgain()` first catches up from the anchors (so deletions since go up), then forgets only how far each type was read, the counts (which the new pass makes again) and when Activity summaries were read, and the app runs it from the start. What deletes records no longer readable (characteristics', prescriptions' IDs), the last upload and the account's rate and storage limits stay: signing out's `reset()` forgets those too. The server keeps one copy of each record, but the iPhone sends everything again, blobs included, so the alert says it can use a lot of data. Detecting a limited history (recent samples, none older than 30 days) to suggest it is left for later.
  - **Health access in the Settings sheet** (851-2775): Health doesn't let apps open their access settings (the app's own Settings page has no Health permissions), so the sheet says where they are, Settings › Privacy & Security › Health › lil health, and offers Health's pickers for what's shared one by one, Choose Medications… and Choose Vision Prescriptions…, after which the app uploads what's newly shared.
- **Statistics:**
  - **Cumulative types** (steps, energy, distance…): the iPhone computes 30-minute sums with HealthKit's own statistics queries, so de-duplication by source priority (e.g. iPhone and Watch steps) matches Health exactly.
    - 30-minute buckets keep days exact in half-hour time zones. Only offsets ending in :45 are approximate.
    - The Mac adds buckets up into days in its current time zone.
  - **Discrete types** (heart rate, weight…): the Mac computes averages, minimums and maximums from raw samples. Averages of bucket averages would be wrong, and HealthKit's statistics don't include sample counts to weight them.
  - Raw samples also back "Show All Data".
  - **On the Mac** (`HealthDatabase`):
    - Cumulative totals come from the statistics source's 30-minute buckets, placed by their start in the Mac's time zone.
    - Discrete averages follow each type's aggregation style:
      - **Arithmetic:** a plain average.
      - **Time-weighted:** each sample counts until its source's next sample, up to an hour, and a source's last one for its own duration. Sources are weighted separately, so a second device's readings don't cut the first's short.
      - **Sound levels:** an equivalent continuous level.
    - The statistics source is the Watch-paired iPhone among those that reported in the last 14 days, then the most recent of those. If none reported recently, it's the most recent of all. Ties go to the higher device ID.
- **Multiple iPhones:** every signed-in iPhone uploads, relying on Health's iCloud sync to give them the same data.
  - Samples de-duplicate by HealthKit UUID.
  - Statistics are stored per iPhone, and the Mac reads one statistics source: the iPhone paired with an Apple Watch, otherwise the most recently active one. An iPhone that's behind on iCloud sync can't overwrite a complete one.
    - Each iPhone's statistics are `health_statistic` rows, keyed by device, type and bucket. Its `health_statistics_device` row records whether it's paired with a Watch and when it last reported, and the Mac picks the source from those rows.
    - Both entities are device-scoped (`docs/SYNC.md`): the server stamps rows with the uploading device.
    - An iPhone that signs out has its device row deleted, and its device-scoped rows are deleted from the store a chunk at a time (`docs/SYNC.md`). So a signed-out Watch-paired iPhone can't stay the source. One that stops without signing out (app deleted, tokens expired) is retired by a daily job once it has no live session and hasn't been seen for a day. Until then, the Mac's 14-day rule skips it.
  - Not supported: Health iCloud sync turned off, or iPhones on different Apple IDs in one lil account. Signing in on a second iPhone shows a warning about this: after sign-in, the app checks `GET /v1/me`'s `devices` once per account for another `health-ios` install.
- **Privacy:**
  - Health data is readable by the server and encrypted at rest by Cloudflare. That keeps server-side features possible, such as the remote MCP server below.
  - It's processed only with explicit consent (GDPR special-category data), and never used for ads or sold.
    - **Consent** is to a privacy policy version, its effective date (`healthConsentPolicyVersion` in `src/core/Consents.ts`). The server records each consent and withdrawal in D1's `consents` table with its time, as proof of consent, and deletes them with the account.
    - `GET /v1/me/consents/health` returns the required version and the consent in force. `POST` with the version the app showed records consent; an older version gets 409 `ConsentOutdated`. `DELETE` withdraws it.
    - New batch uploads without a current consent fail with 403 `ConsentRequired`, before anything reaches R2. A batch the store already knows still answers with its status, and batches accepted before a withdrawal are still applied. Data already uploaded stays until the account is deleted.
    - Bumping the version, for a change in how Health data is used, refuses uploads until each user consents again.
    - **On the iPhone,** the consent screen comes after sign-in and before Health access: what's uploaded, where and why, a privacy policy link, and Agree or Not Now. Nothing is pre-checked. `HealthConsentClient.policyVersion` is the version the screen describes, so bump it with the screen.
      - The iPhone remembers the version it consented to (`healthConsentPolicyVersion` in app storage). Nothing uploads without it, including HealthKit's background wakes and background tasks. Each launch asks the server before uploading, which catches consent withdrawn or given on another iPhone (offline, the iPhone's answer stands). An upload refused with `ConsentRequired` clears it too, in the background as well. An answer that was out while consent was given or withdrawn here is dropped as stale.
      - The screen comes up on its own once per sign-in. After Not Now or a withdrawal, the home screen says nothing is uploading and offers it again.
      - Withdraw Consent in the account section clears the iPhone's consent and pauses uploads at once, tells the server, then offers to delete the account. If the server can't be told, consent stands again and uploading stays paused until the next change or launch.
  - **Command-line and agent access** (851-2840): the `lil-health` command and its MCP server (851-2843) read the Mac's local database, and agents usually send what they read to a cloud model, which the consent screen doesn't cover. So it's opt-in and visible, decided with Alexandru (2026-10-20):
    - The Mac's Settings › Agents has **Allow command-line and agent access**, off by default, with a warning that agents may send what they read to their providers. On or off for all of the Mac's data: no per-category choice.
    - Below it, an **access log** of the latest 100 queries (the command or tool with its arguments, never what it answered; when; the calling process) and Turn Off Access. The open pane reads the log again every 2 seconds.
    - **Storage:** `AgentAccess.sqlite` in the Mac app's folder in Application Support (`HealthDatabase.macDirectory`, `~/Library/Application Support/tech.lil.health/`, next to `Health.sqlite`; spelled out rather than taken from the bundle ID, which the command doesn't have), through the `HealthAgentAccess` module (`AgentAccessStore`), which the app and the command share. A file rather than user defaults, so a separate executable reads and writes it the same way; SQLite, so several processes log at once. It keeps the latest 1,000 entries. Every call opens and closes it. Its tables are made with `CREATE TABLE IF NOT EXISTS`, not a migrator, since two processes may open a new file at once.
    - The command calls `AgentAccessStore.authorize(command:process:)` before **every** query, not once at launch, so turning access off stops a long-running MCP server at its next query. It checks and logs in one transaction. While it's off it throws `AgentAccessError.off`, whose message says where to turn it on.
    - Saves of the setting are dated, and one older than what's saved is ignored, so saves that finish out of order end as the person left it, and one still running at sign-out can't undo the reset.
    - Signing out turns access off and empties the log, like the account's pins and data: the next account decides for itself.
    - It's a consent switch, not a sandbox: anything running as the user could read `Health.sqlite` directly.
    - The privacy policy says so (effective October 20, 2026). The consent version stays `2026-10-15`: nothing changes for what's uploaded or how the server uses it, or for anyone who leaves the setting off, and the setting carries its own warning. The consent version names the last policy change that affected what people consented to, so it can be older than the policy's date.
  - **Agents connected to the account** (851-2845, launched in prod by 851-2855): remote agents (Claude, Claude Code, ChatGPT) read the account's Health data from the server through `https://mcp.lil.tech/health`, once the user allows them. A bigger step than the Mac's local access above: third-party services pull Health data from our servers, from anywhere. The design is in `accounts.md` (Agents) and `server.md` (MCP servers); what it means for privacy, decided with Alexandru (2026-10-20):
    - **Optional, asked each time:** nothing connects unless the user signs in on the authorization page and allows that agent. Nothing is remembered between connections, and there's no account-wide switch.
    - **All or nothing:** an agent reads all of the account's lil health data, read-only (`health:read`), with no per-category choice. Summaries first: the toolkit's aggregate-first tools, with paged samples and a 256 KB ceiling per result. No blobs (ECG voltages, workout routes, documents' XML) for now.
    - **Where it goes:** to the agent's provider (Anthropic, OpenAI…), when the agent asks, under the provider's own policy. We never see the conversation or what the agent does with it.
    - **What we keep:** the grant while it's connected (the agent's name, domain and return host, when it connected and last read; it ends after 90 days unused), an access log of each tool call for 90 days (tool, types, range, outcome, rows; never values, answers or search text), and each agents consent and withdrawal until the account is deleted.
    - **How to stop:** revoke one agent, or Turn Off Agent Access for all of lil health's, in Settings on the Mac (Agents) or the iPhone (Connected Agents); it's cut off at its next request. Or remove it at the provider. What the provider already received stays with it.
    - **Consent:** a separate `agents:health` consent (GDPR Article 9(2)(a)), recorded when the user allows an agent, against its own policy version, `2026-10-21` (`agentsConsentPolicyVersions` in `src/core/Consents.ts`): the privacy policy that describes it. Health consent's version stays `2026-10-15`, so uploads don't stop and nobody consents to Health again: agents only read what Health consent already covers, and the agent consent is asked at connect time. There's no in-app notice of the policy change either: nothing changes for anyone who doesn't connect an agent, and connecting is where it's asked, with a link to the policy's section (`/privacy#agents`).
    - **The privacy policy** says all of this (its section "AI agents connected to your account", `#agents`, effective October 21, 2026), and the help page, [lil.tech/agents](https://lil.tech/agents) (`Web/site/public/agents`), says how to connect Claude, Claude Code, ChatGPT and other agents, what they can read and how to revoke them. Protected Resource Metadata's `resource_documentation` points to it (`staging.lil.tech/agents` on staging).
    - **Prod since 851-2855:** `prod` is in `agentAccessEnvironments`, after the policy, the help page and revoking in both apps, so the OAuth routes and the MCP server answer in every environment, and the apps always show the MCP server's URL (`APIEnvironment.mcpURL(app:)`).
  - Real health data never goes into staging, previews, tests, commits or tickets.
  - **Privacy policy:** at [lil.tech/privacy](https://lil.tech/privacy), under Alexandru Ţurcanu's name, since the apps are published from a personal App Store Connect account. Alexandru is the data controller. The contact is hello@851.sh. The iPhone app links it from sign-in and the account screen. Update its effective date and tell users in the app when a change affects how Health data is used.
- **Summary pins (Mac)** are synced (851-2641): a `health_pin` record per pinned type, keyed by its HealthKit type ID, with a `position`. The Mac reads them from its synced table and writes them through `POST /v1/sync/mutations`, the first entity apps write (`docs/SYNC.md`). A change writes every pin's position and deletes the unpinned ones, a dozen records at most. Two Macs editing at once end with whichever pushed last, record by record. A change is written 300 ms later, so a burst of edits is one write, and each write makes the table match the pins, so the last one wins. Pins a Mac kept in its user defaults from before move up when sync starts, through the push queue, so they show at once and survive the bootstrap that adding the entity brings. They go after any pins the account has, and are cleared once written. Signing out clears them with the rest of the account's data.
- **The Health toolkit for agents** (851-2841): one definition of the tools agents get, served twice: by the API's remote MCP server from the user's store (851-2845, 851-2851) and by `lil-health mcp` on the Mac from its synced database (851-2844). Agents see the same tools, schemas and answers from both. One definition and two implementations, kept honest by shared conformance cases, like the OpenAPI contract.
  - **Defined in `Services/api`** (`src/health/tools/HealthToolkit.ts`) with Effect's `Tool` and `Toolkit` (`effect/ai`), each tool's input, output and failure typed by `Schema`, the definition holding no server code. Ten tools, all read-only and aggregate-first: `summary`, `list_types`, `metric(type, range, statistic)`, `samples(type, range, cursor)`, `workouts(range)`, `sleep(range)`, `medications`, `health_details`, `search(query)` and `sync_status`. No per-category filtering: an agent with access reads everything (`health:read`, 851-2845).
    - Outputs are totals, buckets and short lists, never every sample: `samples` is paged (100 a page, at most 500) and `workouts` lists at most 100, with the period's count and total. The descriptions are written for agents: when to use a tool, and what each field means.
    - Ranges are Health's D, W, M, 6M and Y, ending on an optional `date` (default today, and a day that exists: not 2026-02-31): that day in hours, 7 or 30 days in days, 26 weeks in 7-day weeks, 12 calendar months in months.
    - **Time zones:** every tool takes an optional IANA `timeZone` for its days and local times, and every output echoes the name as given. Only IANA names in their proper case: an offset (`+01:00`) or `europe/london` is an error, though `Intl` takes both, so the two servers can't read one differently. Aliases (`US/Pacific`) are echoed as given, not canonicalized. The remote server defaults to UTC (it doesn't know the user's zone); the Mac to its own. Times are local with their offset, to the second, rounded down (`2026-10-20T08:15:00+01:00`, `+00:00` for UTC); days are `YYYY-MM-DD`. Not Unix milliseconds: agents read these, and both sides format them alike.
    - Every tool is annotated read-only, idempotent, not destructive and not open-world (Effect defaults destructive and open-world to true). A tool's error (an unknown time zone, say) is a `HealthToolError` whose message the agent sees.
  - **`Services/api/mcp-tools.json`** is each tool's name, title, description, input and output JSON Schemas and annotations, exactly as an MCP server lists them: `scripts/mcp-tools.ts` registers the toolkit with Effect's `McpServer` and writes its `tools/list`. `scripts/format` regenerates it with `openapi.json`, and `scripts/format --lint` fails when it's stale. The Mac's server registers its tools from the file, through a Swift copy the same script writes (`HealthCLI/MCPToolsJSON.swift`, below).
  - **Output types in the OpenAPI spec:** each tool's output is a component (`HealthSummaryResult`, `HealthMetricResult`… named in `healthToolResultNames`), with the schemas it's made of (`HealthSummaryMetric`…), so the Swift client has them as generated types, though no endpoint returns them. Only components were added, so installed apps are unaffected. Outputs follow responses' compatibility rules: fields can be added, never removed or renamed, and enum-like output fields (a statistic, a medication's form) are plain strings, so new values don't break clients. Output roots aren't named in the toolkit, so MCP's output schemas stay plain objects.
  - **Conformance cases** (`Services/api/test/health/tools/conformance`): `dataset.json` is a synthetic account in upload form (each iPhone's batches, with its device and when the server received it), and `cases.json` tool calls on it, each with the clock's time, any pins the Mac pushed, and the output both servers must give (or that it fails). Expected outputs are written by hand from the dataset and the descriptions, not copied from an implementation. Outputs match as JSON, with numbers within a relative 1e-9, since sums may be added in another order.
    - The server's side (`Conformance.test.ts`) ingests the batches through `ingestHealthBatch`, as uploads are, and calls tools through the toolkit, so arguments and outputs go through their schemas. Every case runs: the server implements all ten tools (851-2868). Each case also runs against the remote MCP server (851-2851) over Streamable HTTP, checking its structured content and text.
    - The Mac's side (`HealthToolkitConformanceTests`, 851-2844) syncs the dataset into a fresh Mac database with the app's sync engine (one page of the change feed through `LilSyncEngine.pull`, as the server's feed has the batches after ingestion: statistics and the `self` statistics device keyed by the device, with `reportedAt` when the batch arrived; then the pins as `health_pin` upserts), then calls each case's tool through `lil-health mcp`'s server over an in-memory MCP connection. Every case runs: the Mac implements all ten tools. Cases without a `timeZone` expect the remote server's default, UTC, so the Mac runs them as if its own time zone were UTC (`HealthTools.defaultTimeZone`). The conformance files and `mcp-tools.json` count as Swift changes for CI (`.github/actions/changes`), so a case added or changed on the server runs on the Mac before it merges (851-2868).
    - The dataset covers each tool (851-2868): two sources of heart rate with gaps over an hour (time weighting), the Watch's sleep stages against the iPhone's estimates and a nap, medications on a schedule, as needed and archived (a snoozed then taken dose, one taken after midnight), characteristics with one Not Set, glasses and contacts prescriptions, Activity Rings, and a deleted sample. Cases run in UTC, London, Los Angeles, Kolkata (half-hour hours) and Auckland (a birthday that's come).
    - `summary` passes on the server first: for each pinned type (else the Mac's six suggestions: steps, heart rate, active energy, walking + running distance, resting heart rate, weight), the latest sample that has started, and for types that add up, today's and the last 7 days' totals from the statistics source (as the Mac picks it, skipping zero buckets); plus the count and duration of workouts that started in those 7 days, by now (one an app dated later today hasn't happened). Deleted samples the store hasn't swept are skipped (tombstones).
    - **The other nine on the server** (851-2868, `src/health/tools/StoreHealthTools.ts`, a file per tool) port the Mac's `HealthTools` and the `HealthDatabase` queries behind them to the store's SQLite, rule for rule, rather than restating the descriptions, since the conformance cases can't cover every edge. So they keep the Mac's choices: `metric` weighs each bucket's readings on their own (a time-weighted reading near a bucket's end looks an hour past it, no further), a cumulative type's samples count past its last nonzero bucket, `samples` and `workouts` include records dated later today, `search` counts a characteristic as data unless it's `null`, and a workout's statistics are read all or nothing. Types are resolved as the Mac's commands take them (identifier, name or short identifier), names ordered with ICU's collation (`Intl.Collator`, numeric), as `localizedStandardCompare`. Every read of `health_sample` skips tombstones. No blobs (ECG voltages, routes, documents).
  - **The catalog on the server** (851-2857): `list_types` and `search` name each type and its category, `metric` picks its default statistic and averaging by the type's aggregation style, and `workouts` names activities, all as the Mac does. So the server reads the Mac's catalog: `Services/api/health-catalog.json`, generated from the Swift `HealthCatalog` (its categories, every type with its name, kind, categories, unit, aggregation style, availability and read authorization, and the workout activities' names, which moved there from `HealthPages`), and read by `src/health/HealthCatalog.ts`.
    - **Swift is the source of truth,** because HealthKit is: `HealthCatalogSDKTests` checks the Swift catalog against the SDK's headers and HealthKit itself (identifiers, availability, units and aggregation styles), which only Swift on a Mac can do. A JSON source both read was the other choice: the apps would decode it at launch from a resource inside the Swift target, which the Worker would import from outside its workspace, and a catalog change wouldn't trigger the services' deploy. The Swift builders also stay readable, with their comments.
    - `scripts/generate-health-catalog` compiles the module's sources with `swiftc` on their own (a couple of seconds, no package build) and writes the file. `scripts/format` runs it with the Swift part, `scripts/format --lint` fails when the file is stale, and so does `HealthCatalogTests`, so CI's Swift check catches drift either way: a Swift change without the file, or the file edited by hand (it counts as a Swift change for CI). The file is one entry per line, so changes diff by entry.
    - The server decodes the file with `Schema` when the module loads. Its schemas name the Swift enums' cases (categories, kinds, aggregation styles), so a case added in Swift fails the server's tests until the server handles it.
    - **Workout activities** (851-2860): the catalog names every `HKWorkoutActivityType` in the SDK as Health does, deprecated ones included (Dance, for older workouts), and the Mac gives each an SF Symbol. Rest and Group are left out, since the SDK marks them unavailable everywhere. `HealthCatalogSDKTests` checks the names against the header's cases, and `WorkoutFormatTests` that every symbol exists. Only a value a later iOS adds reads "Workout", on both, until it's named.
- **`lil-health`** (851-2843), the Mac's command-line tool, in `lil health.app/Contents/MacOS` and run as `lil health …` (`docs/decisions/distribution.md`).
  - **Commands mirror the toolkit's tools,** with their arguments as options: `summary`, `types` (`list_types`), `metric <type> --range W [--statistic] [--date]`, `samples <type> --range D [--cursor] [--limit]`, `workouts`, `sleep`, `medications`, `details` (`health_details`), `search <words>` and `sync status` (`sync_status`), each with `--time-zone`. Ranges and pages are the tools' (not the ticket's `--from`/`--to`), so the local MCP server (851-2844) calls the same code. Text by default; `--json` is the tool's output, every field there (nulls included, as the schemas require them), so the MCP server can return it as is.
  - **`HealthTools`** implements the tools on the Mac's database, each output a Swift type of the toolkit's schema. They read with the app's `HealthDatabase` queries (statistics source, `cumulativeTotals`, `discreteStatistics`' weighting, `sleepNights`, `MedicationAdherence`…), so answers match the app's screens. `HealthCLI` is the commands, their text and the access check; `Sources/lil-health/main.swift` is the executable. Workout activities are named by `HealthCatalog.workoutActivityName`, as on the Mac's pages.
  - **`metric`'s statistics,** which the toolkit leaves open: for types that add up, `sum` is the total (the default), and `average`, `minimum` and `maximum` are of daily totals over days with data, as Health's Daily Average (of hourly totals for a D range). For other types, statistics come from samples weighted by the type's aggregation style, as the charts', and `sum` is an error. Totals use the statistics source's buckets, then the samples' own past the last bucket, as the charts do; `summary`'s today and 7 days use the buckets only, as the conformance cases expect.
  - **Types** are HealthKit identifiers, as the tools take them, or, for people, the name lil health shows (`Steps`, `"heart rate"`) or the identifier without its prefix (`StepCount`), in any case. `search` also matches identifiers, so `vo2` finds Cardio Fitness. `types` leaves out characteristics (no dates; `details` has them).
  - **Read-only, never migrating:** it opens `Health.sqlite` as a read-only `DatabasePool` (`HealthDatabase.openForReading`), so it reads the app's last commit while the app writes (WAL), and refuses a database with migrations it doesn't know (a newer app) or one missing some (an update the app hasn't run).
  - **Access:** each query calls `AgentAccessStore.authorize` with its arguments (shell-quoted, e.g. `search 'blood pressure'`) and the parent process, before opening the database. `--help` and `--describe` aren't queries. Exit statuses follow `sysexits.h`: 64 usage, 65 a bad type, time zone or date, 69 no database it can read, 77 access off.
- **`lil-health mcp`** (851-2844), the toolkit as a local MCP server on standard input and output, so agents read the Mac's synced data offline, and nothing leaves the Mac but what the agent itself sends on. Agents start it themselves: `{"command": "lil", "args": ["health", "mcp"]}`, or the tool inside the app (`/Applications/lil health.app/Contents/MacOS/lil-health` with `["mcp"]`).
  - **The official Swift SDK** (`modelcontextprotocol/swift-sdk`, MIT moving to Apache 2.0), pinned `exact:` since it's before 1.0. Its `MCP` library builds in Swift 6 language mode with strict concurrency. It brings swift-system, swift-log and eventsource (MIT) into the tool; swift-nio is resolved but only its conformance server uses it.
  - **Tools from `mcp-tools.json`:** the tool can't carry the file as a resource, since a resource bundle doesn't reach a tool in the app's `Contents/MacOS`, so `Services/api/scripts/mcp-tools.ts` writes it into Swift as well, a raw string in `HealthCLI/MCPToolsJSON.swift` that the server decodes as the SDK's `Tool`s. One source and one generator: `scripts/format --lint` fails if either file is stale, `HealthMCPServerTests` checks the copy matches the file and that the tools list exactly as the file has them (nothing the SDK drops), and swift-format leaves the generated file alone.
  - **Calls** decode their arguments as the toolkit's schemas have them (required ones, types, enums, `limit`'s and `query`'s bounds; others ignored), then run `HealthTools` as the commands' `--json` does. Without a `timeZone`, a call is in the Mac's time zone as it is then (Foundation's cached zone is reset first), since a server can run for days while the Mac moves. They answer as Effect's `McpServer` does for the remote server: the output as `structuredContent` and as JSON text, and for the tool's own failure (an unknown type or time zone, access off, no database) `isError` with the message as text. Arguments outside the schema are the request's error (`-32602`, invalid params).
  - **Access:** every call checks and logs (`AgentAccessStore.authorize`) before it opens the database, as a command does: the tool's name and the arguments it takes as JSON (`metric {"range":"W","type":"Steps"}`; others an agent sends are left out, as the tool ignores them), with the agent as the process. Listing the tools and reading the catalog don't need access, so an agent connects while it's off, and each call then says where to turn it on. The database is opened for each call, so a server running since before an update reads once the app has migrated.
  - **Resource:** `health://catalog`, the catalog of categories and types with workout activities' names (`HealthCatalog.json()`, the same as `Services/api/health-catalog.json`), served whether or not access is on, since it isn't the person's data. The remote server should serve it under the same URI.
  - **Adding it:** install `lil` (lil health › Install Command Line Tool…), then in Claude Code `claude mcp add --scope user lil-health -- lil health mcp`. In Codevisor, Settings › MCP servers, add a stdio server with the command `lil` (its full path from `which lil`, since apps don't get the shell's `PATH`) and the arguments `health mcp`. `lil-health mcp --help` says the same, and so does the Mac's Settings › Agents (851-2865), with copyable commands and `lil`'s full path once it's installed (from `~/.local/bin` or `/usr/local/bin`, read again while the pane is open).
  - **Testing on a synthetic database:** `CFFIXED_USER_HOME` moves Foundation's home folder, so `CFFIXED_USER_HOME=/tmp/home lil-health mcp` reads `/tmp/home/Library/Application Support/tech.lil.health/`. `LilHealthExecutableTests` drives the built tool that way (initialize, `tools/list`, `tools/call`); never turn access on for the real database to test.
- **Availability:** permanently free, with no subscriptions, ads or paid tiers.
  - Signup is open, in every App Store region except mainland China (data-localization rules). The server also refuses new accounts from mainland China, since the Mac app is downloaded directly.
    - The server goes by the country Cloudflare gives the Worker (`request.cf.country`, which unlike the `cf-ipcountry` header doesn't depend on a zone setting). `CN` can't create an account (451 `SignUpUnavailableInRegion`), but an existing account still signs in. Hong Kong, Macau and Taiwan have their own codes and aren't affected. A VPN gets around it. That's accepted, since the point is not to offer the service there.
  - Rate limits and per-user storage quotas keep costs in check.
