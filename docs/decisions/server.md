# Server

<!-- Part of docs/DECISIONS.md, the index of decisions (851-2791). -->

- **One API for every app:** a monolith at `api.lil.tech`, used by lil health now and by lil mail and lil calendar later.
  - Environments: prod (`api.lil.tech`), staging (`api.staging.lil.tech`), and a preview per PR.
  - **`mcp.lil.tech`** (`mcp.staging.lil.tech`), the MCP servers for agents (`accounts.md`, Agents), is another custom domain of the same Worker (an alias in `stageDomains`): no second Worker or deploy. The Worker sends each host only its own routes. Previews and personal stages serve both on their workers.dev host.
  - Staging and previews hold synthetic data only. Simulator builds use them; builds on your own iPhone, with your real Health data, use prod under your own account.
- **Hosting:** Cloudflare only for now, on Workers Paid. `lil.tech` is registered at Namecheap, with DNS on Cloudflare.
- **Stack:** Effect 4, Vite+, and [Alchemy](https://alchemy.run) v2 for infrastructure as code (`alchemy.run.ts`).
- **API contract:** Effect HttpApi publishes OpenAPI, with routes versioned under `/v1`. The spec is committed, and the Swift client is generated from it with `swift-openapi-generator`.
- **Storage:**
  - D1 holds data shared across users: users, identities, sessions, devices and connections.
  - **Drizzle for the core D1 database** (851-2686), ahead of lil mail and lil calendar adding core tables. `drizzle-orm` and `drizzle-kit` are pinned to `1.0.0-rc.5-ab785fc`, the exact build Alchemy beta.83 is built against.
    - The schema is `src/core/Schema.ts`. drizzle-kit generates migrations from it into `migrations/core`, in its own folder format (`<timestamp>_<name>/migration.sql` plus a snapshot), which Alchemy's D1 resource applies on deploy.
    - Migrations are generated in the repo, never at deploy: `scripts/format` runs drizzle-kit, and `scripts/format --lint` fails if the schema changed without a migration (`scripts/migrations.ts`). Alchemy's `Drizzle.Schema` resource, which generates during deploy, isn't used.
    - What Drizzle can't express (the Apple token revocation trigger) is SQL appended by hand to a generated migration, after a `--> statement-breakpoint` (the only place Alchemy splits statements).
    - Alchemy picks one migration format per folder. Mixing our old numbered `.sql` files with Drizzle's folders would have hidden the old ones, which Alchemy then treats as rewritten history.
    - Repositories query `CoreDb` (`src/core/CoreDb.ts`): Drizzle over D1 in the Worker (`drizzle-orm/effect-d1`) and over Node SQLite in tests (`drizzle-orm/effect-sqlite-node`), one type for both. They keep failing with `SqlError` (`query()` unwraps Drizzle's error to the driver's), so callers didn't change. Every core repository is on Drizzle (851-2687, 851-2688), and the Worker no longer provides `SqlClient` for the core database. Queries the builder can't express (Consents' race-safe `INSERT … SELECT … WHERE NOT EXISTS`) use Drizzle's `sql` template over the schema's columns.
    - The per-user store stays on raw SQL: its bulk upserts are hand-tuned, and its migrations must stay additive, which drizzle-kit's table rebuilds don't respect.
  - **The October 2026 wipe** (851-2686): with no users, we started over instead of carrying the old migration history.
    - The core database's resource ID changed (`Core` → `Core2`), so Alchemy created a fresh database from the Drizzle baseline and deleted the old one.
    - The store's Durable Object ID changed (`UserStore` → `UserStore2`), so Alchemy deleted the old class and Cloudflare deleted every store of it. Under the same ID, a renamed class would have kept its data.
    - R2 buckets stayed. Objects of users the new database doesn't know, and snapshot parts uploaded before the cutover, were deleted by a one-off script.
    - Health batches still queued at cutover are dropped: ingestion skips users the core database doesn't know, so it can't create a store for nobody.
  - IDs are a type prefix plus a 26-character time-sortable code (e.g. `usr_01jb…`), with branded Effect Schema types. Times are Unix milliseconds.
  - Each user's own data (health now, mail and calendar later) lives in that user's SQLite-backed Durable Object.
  - A store migrates its own schema the first time it's used after a deploy, from migrations listed in code (`src/store/Migrations.ts`). Migrations are additive only, because a rolled-back Worker can meet a store that newer code already migrated. The migrator is ours, not Alchemy's `SqlMigrations`, so it runs in tests on `node:sqlite`.
  - Large blobs (ECG voltages, workout routes, sync snapshots) live in R2.
  - R2 blobs are immutable and addressed by content hash. They're only deleted with a grace period (or when an account is deleted), and snapshots can be rebuilt from the Durable Object.
    - Health blobs no record refers to (e.g. an ECG deleted in Health) are deleted by the user's store 35 days after they lost their last reference, longer than the 30 days of point-in-time recovery (`docs/SYNC.md`).
  - The exception is uploads waiting to be applied, such as health batch files. They're staging, not data: keyed by user and batch, deleted once applied, and expired by a 7-day lifecycle rule if anything leaves them behind.
  - **Deleting R2 objects** (851-2655, `deleteObjects`): 100 keys per call, 6 calls at once, not R2's limit of 1,000 per call. A call takes as long as its slowest keys, and R2 has slow spells (the same deletes took 10 times as long from one run to the next, and deletes just after many writes were slow too). On a personal stage, a store deleting 2,000 objects that had aged 15 minutes took 6.3–8.1 s with 1,000-key calls one at a time, and 1.7–1.9 s with 100-key calls six at once, alternating over three rounds. That's about 9 s for 10,000. More than 6 at once wasn't faster, since a Worker keeps at most 6 connections open. A 1,000-key call took up to 48 s in a slow spell, and prod's wipe of 2,644 snapshot parts took minutes per call. No call was throttled (10058) in these runs; a throttled call is tried again, and with smaller calls that's only 100 keys.
  - Not D1 for user data, because one D1 database has a hard 10 GB cap shared by everyone, and a Worker can't bind a new database per user at runtime.
- **Backups:** D1 and Durable Object point-in-time recovery (30 days). R2 has none, which is why blobs are immutable.
- **Storage quota:** each user's store may grow to 8 GB, below the 10 GB a Durable Object can hold. The size is SQLite's used pages (workerd's `databaseSize`), so deleted records make room once the change log is compacted. Health blobs in R2 count towards the same 8 GB.
  - At the quota, new batch and blob uploads fail with 507 `StorageFull`, before anything reaches R2. A batch or blob the store already knows still answers.
  - Batches accepted before the quota are still applied, because the iPhone never sends a batch again once it's accepted. The gap up to the cap absorbs them.
  - On the iPhone, a 507 ends the backfill run, since every other upload would be refused too.
    - The pending page is kept so it goes up once there's room, and types the run didn't reach are asked for again.
    - The sync status screen shows **Storage full** with Try Again.
    - While full, syncs for changes wait 6 hours between tries, and no background task is requested. Opening the app and Try Again always try.
    - The first upload that goes through clears the state.
  - At a 9.5 GB hard limit, writes of new records fail too, so the store never reaches the cap. Deletes still apply. A queued batch that meets the limit fails ("The storage quota is full; N lines were applied before it") rather than retrying.
  - **Largest users:** after applying each health batch, the queue consumer records the account's storage in D1 (`users.storage_bytes`, `storage_measured_at`): the store's size plus its health blobs'. Batches are where the store grows, and blobs are uploaded just before the batches that refer to them, so the figure lags uploads only briefly. Measurements that arrive out of order don't overwrite later ones, and recording is best-effort. To list the largest users, run `Services/api/scripts/largest-users.sql` in the D1 console for the stage's core database. It shows only IDs and sizes, and tests run that same file.
  - Every error a store returns is listed in `userStoreErrors`, so it crosses Durable Object RPC as itself. Test stores pass any other error as a plain object, as RPC would, so a missing entry fails the tests.
- **Health ingest throughput** (851-2647, measured on a personal stage with synthetic step samples, 20k-item batches):
  - A user's store (one Durable Object, one thread) is the ceiling for that user. Batches apply in store calls of up to 5,000 lines or 4 MB, the consumer reads the next chunk while one applies, and the queue applies at most 2 batches at once. This went from 1,926 to 5,280 items/s end to end.
  - The limit of 2 (raised to 4 below) is global, not per user: 3 overloaded the store, failing uploads with 503, and 1 left it idle between batches (2,657 items/s). Smaller calls (2,000) were slower (2,962 items/s) at the same upload latency.
  - Most of the store's CPU (about 150 of 200–220 µs per item) went to inserting HealthKit's random UUIDs into the `id` index; time-ordered IDs cost 59 µs. So samples are stored by type and start date, with no index on `id` alone, and deletes leave tombstones that the alarm sweeps (851-2651, `docs/SYNC.md`). With real random UUIDs that's about 80 µs per item and 6,594 items/s end to end. The store is then about half busy, but a limit of 3 was still slower (3,401 items/s, with uploads up to 3 s), so it stays 2.
  - **4 batches at once** (851-2675) since applying got cheaper: grouped upserts (851-2671) and a change log without row copies (851-2673, 851-2676). A consumer invocation then took about 1.5 s for 0.4 s of store time, so 2 left the store idle. On a personal stage (synthetic, 200,000 samples, 4 uploads in flight), 4 applied 3,417–4,686 items/s against 2's 2,544–3,293 with 2,500-record batches, and 4,624–6,538 against 4,242–5,366 with 5,000-line batches (4 MB calls). Upload latency was the same (about 0.5 s median), with no 503s or overloaded errors over two hours of runs. Calls hold at most 2 MB of line text (was 4 MB), so 4 consumers sharing an isolate keep the memory 2 had.
  - **4 batches at once per user** (851-2652), not globally. Each user's store takes at most 4 batches at once (`healthBatchesAtOnce`), holding each one's place in memory until it's applied or fails (or for 2 minutes, if it never says). A store that restarts starts with none. A batch whose turn hasn't come is sent back to the queue as a new message, delayed, so waiting holds no consumer and doesn't use up its 5 retries. Its `queued` timeout restarts each time.
    - **Order:** batches start in about the order they were received, so a later batch (say, a deletion) can't be applied before an earlier one it undoes. Only the 8 oldest waiting batches may take a free place. A waiting batch is one still `queued` that was received or turned away in the last minute, so a batch whose message was lost stops holding others back after a minute. A retry after a batch failed partway carries on, ahead of the line.
    - **Waits:** the 8 next in line ask again after a second. Others ask again after a quarter of a second for each batch ahead of them, up to 20 s, so a long backlog costs a few store calls a second. In load tests a batch was delivered about 4 times.
    - **Consumers:** the queue handles 16 messages at once across users (`healthBatchConsumers`), two users' batches plus those being turned away. With 8, two users got about 4,600 items/s each, because the turned-away messages queued behind the applying ones. Not more, because consumers can share an isolate and each applying batch holds up to two 2 MB chunks and their mutations.
    - **Measured** on a personal stage (synthetic, 120,000 samples a user, 5,000-line batches, 4 uploads in flight): one user applied 8,261–9,486 items/s (5,263–6,578 with the global limit), and two users at once 6,235–9,054 items/s each, with no failed uploads or invocations. A deploy that changes the consumer's settings paused delivery for about a minute.
  - **5,000-record batches from the iPhone** (851-2677): with the server the ceiling, smaller batches cost more than they save. With 4 consumers, 2,500-record batches applied at 3,417–4,686 items/s (4 MB calls, which they never reach) and 5,000-line ones at 5,872–7,851 (2 MB calls, so two per batch, the second read while the first applies). The test kept 4 uploads in flight; the iPhone keeps 2 (a 10,000-object page), but uploads a page in about one upload's time, faster than the server applies, so the queue stays full either way and the batch size sets the rate. A retried batch resends and re-applies up to 5,000 records.
  - **2,500-line store calls** (851-2667), down from 5,000. Uploads call the user's store twice (checking the batch before it's stored, recording it as queued after), and each waits for the transaction the store is running. During a backfill on a personal stage (synthetic, 200,000 samples, 2 uploads in flight like the iPhone), those two calls waited 300–650 ms at p90 with 5,000-line calls, and 120–360 ms with 1,000 or 2,500. The rest of an upload was the R2 put (about 200 ms, with outliers past 2 s) and the queue send (about 90 ms), so the server took about 0.4 s at p50. At full speed (4 uploads in flight, six alternating runs each), 2,500-line calls applied a median of about 4,900 items/s against 5,000's 3,970. Both were noisy (1,313–9,415 items/s), and lower than 851-2677's runs on the same setup, so this shows 2,500 isn't slower, not that it's faster. A batch of 5,000 records is now two calls of 2,500. Before, the 2 MB limit cut it into one call of about 4,900 step samples (about 430 characters each) and a small remainder. Overlapping the R2 put with the checks would break "before anything reaches R2" for consent and the quota, so it doesn't. Recording the batch as queued only once the consumer starts it would save the second call, but status reads and the order batches start in (851-2652) rely on that row existing from the upload.
  - Prod's one store (the developer's own data) is emptied by deleting the account before that deploy, rather than migrated in place, since copying millions of rows at the store's start could exceed a Durable Object's CPU limit.
- **Provenance stored once** (851-2674): a sample's source revision and device (about 200 of a step sample's 490 bytes) repeat across nearly all of a user's samples, so they're a `health_provenance` record, keyed by a hash of the pair, that records refer to by `provenance` (`docs/SYNC.md`). The iPhone's `HealthBatchWriter` does it for every entity with a source and device, writing each pair once per file, so files stay independent. Older iPhones keep sending them inline, so the server and the Mac take both, and the Mac's sync schema went to 2 so it bootstraps again and gets `provenance`. A Mac from before shows no device or source revision for records from an updated iPhone; none was released (Mac distribution is 851-2632), so no installed app was left behind. On a personal stage (synthetic step samples, 5,000-record batches applied one at a time, three alternating rounds), batches applied in 713 ms on average against 897 ms inline. A line is 372 bytes instead of 492 before compression, and 5% smaller after. The rows the store and the Mac keep lose the same 200 bytes. With 4 batches at once the difference was lost in the noise.
- **Mac sync throughput** (851-2649): writing a change cost much more than the change itself. StructuredQueries built each row's upsert (`ON CONFLICT` and all) for 68 µs, against 3 µs through one prepared statement. So every synced table upserts through one cached statement (`PreparedUpsert`, with GRDB as a direct dependency), built from the table's StructuredQueries columns and binding each record's values in their order (851-2661; until then only `healthSamples` and `healthStatistics` did, with column lists written by hand). In Release (`UpsertBenchmarks`), a workout upsert went from 68–72 µs to 9–10 µs. A sample costs 9 µs, against 4 µs with its values listed by hand: reading each column through a key path costs that much, a few percent of a sample's 130 µs end to end, for no column lists to keep in step. A record with a value StructuredQueries binds specially (a date, an empty blob) is upserted its usual way instead, so nothing is stored differently. With 5,000-change pages and the next page downloading while one is written, a catch-up of 50,000 samples went from 14.2 s to 6.6 s (Release). Bootstraps download four snapshot parts at a time (each file once), hashing and writing them off the sync engine's actor, and parts whose URLs expire together share one refresh. What remains is decoding each page into OpenAPI's generic containers and re-decoding rows; going further would mean an endpoint that sends changes as NDJSON.
- **Sync throughput benchmark** (851-2650): `scripts/bench-sync` (or `vp run bench` in `Services/api`) uploads synthetic Health batches in the iPhone's format to a personal stage, waits for them to apply and for a snapshot, and bootstraps the Mac's real `LilSyncEngine` from it, printing each stage's items per second. Results, and what each stage measures, are in `docs/BENCHMARK.md`; add a run there when a change affects throughput. On 2026-10-21 (1M records) applying was the slowest stage after HealthKit's reads (6,700 items/s), at about 8,200 items/s against every other stage's 14,700 or more, and the Mac's inserts slowed as its tables grew.
- **MCP servers for agents** (851-2851; the OAuth side is `accounts.md`, Agents): each app's server is a path on the MCP host, `https://mcp.lil.tech/health` now (`https://mcp.staging.lil.tech/health`, `<origin>/health` on workers.dev), which is also its OAuth protected resource. Later apps get their own paths (`/mail`, `/calendar`). Like the OAuth routes, they're only where `agentAccessEnvironments` allows, and left out of the OpenAPI spec.
  - **Transport:** [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http), `POST` only. `DELETE` ends a legacy session; anything else is 405 (`Allow: POST, DELETE`). There's no `GET` stream, and no `2026-07-28` subscriptions (`subscriptions/listen` is method not found): the tools never change, and a subscription would hold the store and a connection open. Requests are at most 64 KB (413), since the store holds a body in memory.
  - **The Worker** (`src/mcp/McpRoutes.ts`) refuses a browser `Origin` with 403, as the transport requires, before anything else. It takes only an agent access token in `Authorization: Bearer` (never the query string) and checks it with `AgentTokens.verify(token, <the app's resource>)`, so another app's tokens and the apps' own JWTs are refused. Missing, invalid, expired or revoked gets 401 with `WWW-Authenticate: Bearer resource_metadata="<mcp host>/.well-known/oauth-protected-resource/health", scope="health:read"`, plus `error="invalid_token"` when a token was sent: Claude only starts sign-in on a 401. A grant without the app's scope would get 403 `insufficient_scope`, though the app's tokens always carry it. A database failure while checking the token is a 503 with `Retry-After`, not a 401, so agents try again rather than sign in again. Then the `agent` rate limit, then it hands the request to the user's store (`UserStores.mcp`, as `/v1/sync/live` does), setting `x-lil-agent-grant`, `x-lil-agent-client` and `x-lil-agent-scopes` over any the client sent, and dropping the token. The scopes header is the scopes the server may use: the grant's at an app's own server, and at the combined one those of the apps it may read now (below), which choose its tools.
  - **The server runs in the user's store** (`src/health/tools/HealthMcpServer.ts`, served by `src/mcp/StoreMcpServer.ts`): Effect's `McpServer.layerHttp`, with the Health toolkit's handlers on the store's SQLite. The store's `fetch` sends `/health` and `/` (the combined server, below) to its MCP servers (`src/mcp/StoreMcpServers.ts`) and everything else to live notices. The store is the one long-lived place per user, where the data already is, so the older protocols' sessions can live there too. It's built on the first MCP request (again on the next one if that fails) and lives as long as the object, in a context of its own (a fresh router and memo map, the store's clock), on Effect's sync scheduler, which Effect advises for fibers shared by requests on Workers. The fallback the ticket allowed, a request-scoped server in the Worker calling store RPC, would have served `2026-07-28` only.
  - **Protocols:** `2026-07-28`, which needs no session, plus `2025-11-25` and `2025-06-18` for clients that haven't moved yet (Claude is still rolling `2026-07-28` out). Their `Mcp-Session-Id` sessions are kept in memory: a store evicted while idle forgets them, and the client starts a new one after the 404, as the spec requires. Only the user's own agents reach their store, so any of them may end a session.
  - **Tools:** every one needs `health:read`, the one Health scope, which the app's tokens always carry: no per-category filtering, and no missing-scope tool error. Each tool is annotated read-only, idempotent, not destructive and not open-world. It lists and implements all ten tools of `mcp-tools.json`, as the Mac's server does (`summary` first, the other nine in 851-2868).
  - **Data minimisation:** the toolkit's own caps (aggregate-first, paged samples), plus a ceiling of 256 KB per result as JSON. Over it, the call is the tool's error, asking for a shorter range or a smaller page. No blobs in v1 (ECG voltages, workout routes, locations).
  - **Access log:** every tool call adds a row to `agent_access_log` in the user's store (an additive store migration; not synced), before its answer goes back, so nothing is read without a row: the grant, the agent's name, the tool, the types, range and day asked for, the outcome (`ok`, `error` or `too_large`), how many rows went back (the items of the answer's lists), and the time. Never `search`'s text or any values. Listing tools isn't logged, and neither are calls refused before they reach a tool (an unknown tool, arguments that don't fit its schema), which read nothing. It keeps the newest 10,000 rows, trimming the oldest as it adds, and the store's alarm deletes rows past 90 days, waking at most a day after the oldest turns 90. The apps read it through `GET /v1/me/agents/access-log` (851-2852, `accounts.md`), and the data export includes it.
  - **Workers Logs** get the tool, grant, duration and size of each call only.
  - **One call at a time** (851-2887): a store runs its agents' tool calls one after another, each starting in a JavaScript task of its own, and refuses with a tool error ("busy… try again") a call that had waited more than 10 seconds when its turn came (`healthMcpMaxWaitMs`). The store's SQLite reads are synchronous, so calls never ran in parallel, but the server's fibers run on the sync scheduler, which continues in microtasks, so calls sent at once ran back to back in one task. Workers only commits a store's writes (the access log rows) and sends its answers once a task ends, and resets a store when a storage operation waits about 30 seconds, or when its CPU time since its last incoming request passes 30 seconds. On prod, an agent's eight calls at once took longer than that together, and all of them failed with a 500. The wait limit keeps a burst of calls under the CPU limit; a single call of 30 seconds would still be too long. Calls refused for waiting aren't in the access log, since they read nothing. The queue is the store's, shared by all the user's agents and every MCP server in it (lil health's own and the combined one, 851-2900), as its one thread is.
  - **The combined server** (851-2900, `src/mcp/CombinedMcpServer.ts`): every app's tools at the MCP host's root, `POST https://mcp.lil.tech` (`https://mcp.staging.lil.tech`, the origin on workers.dev), the combined resource of `accounts.md` (Agents › The combined server). Only where `combinedAgentEnvironments` allows, so prod answers 404 until 851-2903. Each app's own server stays as it is.
    - **The route** (`McpRoutes.ts`) is an app's, with the combined resource: the same `Origin`, method and body rules, only the combined resource's tokens (an app's own are refused, as combined ones are at `/health`), and a 401 whose challenge names the root metadata (`/.well-known/oauth-protected-resource`) and every app's scope. The same `agent` rate limit, keyed by the grant, so a combined connection shares its 120 a minute across its apps. `firstUsedAt` is recorded as at an app's server.
    - **Which apps:** those whose scopes the grant has, less those whose agents consent (`agents:<app>`) is no longer in force: one read of `consents` per request (`Consents.inForce`). So turning an app's agents off cuts combined grants off from it at their next request, before 851-2901 narrows their scopes, and that stays as a second check after. A grant with no app left gets 403 `insufficient_scope`. The Worker sends the apps' scopes in `x-lil-agent-scopes`, and the store serves only those apps: `tools/list` lists only their tools, and calling another app's tool is an unknown tool (`-32602`), as is a name without an app.
    - **Names:** each tool as `<app>.<tool>` (`health.summary`), as `lil mcp` names them (`distribution.md`), with the same title, description, schemas, annotations and handler; the separator is one constant (`toolNameSeparator`). Effect's `McpServer` takes dotted names. Resources would keep their URIs, as in `lil mcp`, since each app's scheme sets them apart; the remote servers have none yet. The server is named "lil", and its instructions say how tools are named, then give each app's own under its name.
    - **In the store:** a server per set of apps, built on its set's first request, like lil health's, and kept while the object lives. Effect's server lists every tool it has, whoever asks, and a tool's visibility can't see the request, so filtering by grant means a server per set (at most 2^apps). Its protocols and sessions are the app's server's. A session belongs to its set's server, so one whose grant loses an app gets a 404 and starts again, without that app's tools. Tools are registered through the app's own registration (`StoreMcpApp`), renamed as they're added, so the handlers are the app's server's: the same results, 256 KB ceiling and access log row, with the tool's own name (`summary`) and the grant, which shows it came through the combined server. The store's queue of calls (851-2887) is shared by every server in it.
    - **An app column in the log** waits for a second app, when each app's servers record theirs and each app shows its own rows.
    - **Tests** use a fake lil mail (`test/mcp/TestMailApp.ts`, with the registry 851-2899's tests use), whose `summary` shares lil health's name: names don't collide, each call reaches its app, and scopes and consents filter the list and the calls. The conformance cases run through it too, as `health.<tool>`.
  - A forwarded request (MCP, live notices) that a store's reset ended (`durableObjectReset` on the error) gets a 503, like the store's other transient failures, not a 500: the next request starts the store again (851-2887). Store RPC calls keep treating a reset as a defect, since one that writes may have committed before it.
- **Workers Logs without query strings** (851-2908): the API Worker's observability (`apiObservability`, `src/Worker.ts`) turns on logs and invocation logs, as Alchemy's default does (which any `observability` prop replaces), and Cloudflare's `redactQueryString`. Each request's event keeps its method, URL without the query, path, status and headers (Cloudflare masks `Authorization` and `Cookie`).
  - **Why:** query strings carry secrets, and Cloudflare records the request URL before the Worker runs, so no code of ours could hide them. Prod's logs showed the Google callback's `code` and `state`, the one-time `ticket` of `/oauth/authorize/signed-in`, and the agent's `state` and PKCE challenge on `/oauth/authorize`. Signed downloads' `token`s (snapshot parts, blobs, exports: 15-minute bearer URLs) were there too.
  - **Not affected:** bodies and response headers aren't logged, so Apple's `form_post`, `/oauth/token`'s and `/oauth/revoke`'s forms, and the `code` and `state` in redirects to agents (`Location`) never were. Effect's request log line (`HttpMiddleware.logger`) strips the query itself, and our own log lines name no codes, states, tickets or tokens.
  - **Cost:** no route's query shows in Workers Logs, including harmless ones (`/oauth/authorize/consent?request=…`, sync's `after`, the access log's `before`). To follow a request, use its path, status, time and `cf-ray`, or log the parameter you need from the route. The setting is per Worker, and Cloudflare has no per-route or per-parameter redaction. Events logged before it expire with Workers Logs' retention.
  - Answering Google with `response_mode=form_post` instead would have fixed only that callback, and a cross-site post brings no `SameSite=Lax` cookie, so it would need Apple's ticket step too.
- **Billing and usage notifications:** Cloudflare emails alexandru@851.sh when the month's spend reaches $25 and again at $100. It also emails when Workers requests, Durable Objects requests, or D1 rows read or written pass what Workers Paid includes, and when R2 class A or B operations pass R2's free tier, meaning we've started paying for them.
  - Queues and CPU time have no usage alerts, so spend covers them.
  - The policies are account-wide, not per stage, so they live in `Services/api/scripts/notifications.ts` rather than the Alchemy stack. That also keeps the CI deploy token free of notification permissions.
  - To change them, edit the script, then run `node scripts/notifications.ts` from `Services/api` (add `--dry-run` to preview). Don't use `vp run`, whose tasks are cached and don't see your environment. It matches policies by name and leaves others alone. It needs `CLOUDFLARE_API_TOKEN` with Notifications: Edit, or an Alchemy OAuth login that was granted the notifications scopes, which "Basic Scopes" doesn't include.
- **Rate limits** (`src/RateLimits.ts`), counted with the Workers rate limiting binding:
  - Sign-ins: 60 a minute per IP address (`cf-connecting-ip`), shared by Apple, Google and dev sign-in, and the agents' authorization page (starting a request, signing in, and Apple's and Google's callbacks each count). They're unauthenticated and create accounts, so the address is the only key there is.
  - Refreshes: 600 a minute per IP address, separately, so sign-in attempts can't block refreshes, and every device behind a carrier NAT can still refresh.
  - An IPv6 address counts by its /64, since one client usually has a whole /64.
  - Dynamic client registrations for agents (`POST /oauth/register`): 300 a minute per IP address, separately. High, because hosted agents register from shared egress ranges: Claude registers a client per connection, from `160.79.104.0/21`.
  - Agents' token requests (`POST /oauth/token`): 60 a minute per grant for refreshes, and per authorization (the grant it makes) for code exchanges, separately. Not per IP address, since Claude and ChatGPT refresh from shared egress ranges, and not per client, since a client ID is public and shared by every user of a hosted agent, so anyone could use up its budget. Unknown codes and tokens aren't counted: there's nothing to count them against, and each costs one indexed read.
  - Agents' MCP requests (`mcp.lil.tech/health`, 851-2851, and the combined server, 851-2900): 120 a minute per grant (one agent's access to one app, or to every app it reads through the combined server), counted after the token is verified, separately from the apps' per-user limit so a busy agent can't stall sync. Not per IP address, for the same reason as token requests.
  - Authenticated requests: 600 a minute per user, counted after the access token is verified, so a bad token costs nobody's budget. That includes the live socket. Signing out isn't counted, because a refused sign-out would leave the refresh token working.
  - Over a limit, the API answers 429 `TooManyRequests` with `retryAfterSeconds` (and `Retry-After` on routes outside the HttpApi). The apps wait it out. The Mac's sync waits at least `retryAfterSeconds` before trying again. The iPhone's backfill pauses (it isn't a failure) and keeps its page: syncs for changes wait until the time is up, while a run of everything (opening the app, Continue, a background task) waits it out, showing as running, and carries on, including when the 429 comes partway through. A rate-limited refresh keeps the session.
  - Counting is approximate and per Cloudflare location. It's also permissive: on a preview, a burst got a few hundred requests past a limit of 60 before 429s began. That's still enough to bound abuse. A Durable Object would count exactly, but would add a hop to every request.
  - If the binding fails, the request goes through. An outage of rate limiting shouldn't take the API down.
  - Each stage has its own namespace IDs (a hash of the stage name), since bindings that share an ID share counters across the account.
  - Snapshot part downloads aren't limited: their URLs are signed and short-lived.
